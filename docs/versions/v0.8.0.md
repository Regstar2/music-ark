# MusicArk v0.8.0 — Controlled Sync

## Product contract

v0.8 adds a controlled orchestration layer over the existing library pipeline:

```text
Yandex Library (desired state)
        ↓
active collection scope
        ↓
Coverage / Matching / Variant / Local Library (actual state)
        ↓
Sync Planner — read only
        ↓
immutable dry-run Sync Plan
        ↓
preview + blockers + explicit confirmation
        ↓
execution-time revalidation
        ↓
DownloadService.enqueue() for current Missing + Wanted only
        ↓
Downloads page / normal v0.7 transfer workflow
```

This is **not** a bidirectional filesystem mirror. Applying a v0.8 plan means executing only explicitly supported safe operations. The primary automatic operation is enqueueing confirmed `missing + wanted` provider identities into the production download queue.

## Authoritative inputs

Controlled Sync does not reimplement Coverage, Matching, Variant detection, downloading, or Local indexing. It reads:

- active `provider_collection_snapshots` / `provider_collection_items`;
- `CoverageRepository` derived `covered / missing / needs_review / not_analyzed` state;
- `matching_results` and accepted `track_links` through Coverage;
- `provider_track_actions` (`wanted / ignored / unreviewed`);
- `track_variant_results` through Coverage;
- Local Library fingerprint/current indexed files;
- current v0.7 download target;
- active `provider_download` queue rows for deduplication.

Provider identity is `(provider_id, external_id)`. A track in Liked and multiple playlists appears once in an all-library plan. Playlist duplicate occurrences are also deduplicated while playlist position remains available to the Coverage layer/UI.

## Scopes

Supported scopes are:

```text
all        — all unique identities in active cached Yandex collections
liked      — active "Мне нравится"
playlist   — one active cached Yandex Playlist collection id
```

Plan generation is local/cache-only and does not require a Yandex network request. Removed/inactive cached collection identities are not desired state.

## Planning policy

Primary truth table:

```text
covered                         → summary only / no acquisition
missing + wanted                → ENQUEUE_DOWNLOAD
missing + unreviewed            → USER_DECISION_REQUIRED
missing + ignored               → summary only / no acquisition
needs_review                    → REVIEW_IDENTITY
not_analyzed                    → REVIEW_IDENTITY(reason=matching_required)
covered + UNCERTAIN             → REVIEW_VARIANT
covered + ALTERED               → REVIEW_VARIANT
covered + DIFFERENT_VERSION     → REVIEW_VARIANT
covered + SAME / NOT_CHECKED    → no destructive action
```

`DIFFERENT_VERSION` is never treated as Missing and never triggers a replacement download. v0.7 direct single-track **Скачать** remains a separate explicit-user-intent workflow and does not loosen bulk Sync policy.

Local files without a link into desired scope can be shown as `LOCAL_ONLY`. In playlist scope the UI calls this **Outside this scope**. It is informational only.

## Operations

Production v0.8 operation types are:

```text
ENQUEUE_DOWNLOAD
REVIEW_IDENTITY
REVIEW_VARIANT
USER_DECISION_REQUIRED
LOCAL_ONLY
```

Historical operation enum values remain readable for old plans, including upload/replace/metadata candidates, but the v0.8 executor refuses legacy plans. Production planning never creates upload, replace, metadata-edit, local delete/move/rename, or Yandex mutation operations.

Operation execution state is persisted independently from immutable operation intent:

```text
pending
enqueued
skipped
failed
informational
```

## Plan snapshot and staleness

Each plan stores:

- plan id / creation time;
- planner version (`1` for v0.8);
- scope type/id;
- target root id and exact target folder;
- stable input fingerprint;
- status and summary;
- immutable operation intent/metadata;
- apply timestamp/result separately.

Plan states:

```text
planned
stale
applied
partially_applied
cancelled
failed
```

The fingerprint covers relevant active membership, current Coverage/Matching identity state, Local Library fingerprint, wanted/ignored triage, Variant review state, download target, scope, and planner version. Playback position/current track/player queue are deliberately excluded.

When relevant state changes after plan creation, a `planned` plan becomes `stale`. Stale Apply is disabled/refused and a new plan must be built.

## Apply semantics

Apply requires explicit confirmation. It performs:

```text
plan-version / status check
→ staleness fingerprint check
→ target check
→ per-operation execution-time Coverage/action recheck
→ active queue dedup check
→ DownloadService.enqueue(external_id)
→ persist task id/result
```

Apply **does not call `runQueue()`** and does not start unrelated queued work. The baseline result is enqueue-only; the user controls transfer execution from **Загрузки**. Repeated Apply is idempotent and cannot create a second active task for the same identity.

Even after a plan-level validation, every pending download is rechecked. A track that became Covered is persisted as a skipped operation (for example `already_covered`) rather than downloaded again.

## Safety gates

A normal v0.8 Sync Apply must produce exactly zero:

```text
deleted local files
renamed/moved local files
modified tags/metadata on existing local files
Yandex likes/playlist mutations
Yandex uploads/replacements
```

No credentials, authorization headers, Yandex token, or temporary direct URLs are stored in sync tables.

## Storage — schema 1.8.0

The forward migration extends the existing `sync_plans` and `sync_operations` tables in place. It does not introduce `sync_plans_v2`.

`sync_plans` gains v0.8 snapshot/execution fields such as planner version, scope, target, input fingerprint, applied timestamp, result JSON and update timestamp. `sync_operations` gains status, result JSON and update timestamp.

Existing legacy sync rows remain readable and are marked by default as planner version `0` / `legacy`. All Yandex cache, credentials, Local Library, Matching, Variant, Coverage actions, Download state/settings, and sync history are preserved by forward migration.

## Audit

v0.8 records:

```text
sync_plan_created
sync_plan_stale
sync_plan_cancelled
sync_plan_apply_started
sync_operation_enqueued
sync_operation_skipped
sync_plan_apply_finished
```

Audit details contain identities/task ids/reasons only, never secrets.

## UI

Primary navigation becomes:

```text
MusicArk
├── Яндекс Музыка
├── Локальная библиотека
├── Сопоставление
├── Недостающие
```

The Sync page exposes scope, current download target, plan creation, Current vs Projected coverage, grouped operations/blockers, stale/legacy banners, explicit Apply confirmation, Downloads/Matching navigation, plan history, and planned-plan cancellation.

## Validation

Automated coverage includes the planning truth table, Variant policy, scope/dedup semantics, ignored/direct-download history, active queue dedup, one-download rebase regression, membership/local/triage/target staleness, execution-time revalidation, confirmation, DownloadService delegation, repeated Apply, legacy-plan refusal, migration preservation, and Flutter Sync interactions.

Manual Windows validation remains mandatory before release acceptance; see `docs/testing/manual-test-plan.md`.
