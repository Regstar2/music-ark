# MusicArk v0.14.0 — Large Library Performance & Release Hardening

Status: implementation branch / Draft PR #30. No GitHub Release, tag, installer or production auto-update is created by this version.

## Goal

v0.14.0 freezes the pre-release product scope and removes measured or directly demonstrated unnecessary work on large cached libraries. It does not introduce a new provider, audio format, Matching/Variant algorithm, state-management framework, database engine, persistent Python daemon or user-facing product capability.

The main rule is:

> remove proven redundant work rather than redesigning the application for hypothetical scale.

## Baseline hotspots confirmed on v0.13

The v0.13 source state demonstrated the following concrete issues before optimization:

- opening Local Library called `_reload()` and then recursively scanned configured roots;
- the Local Library backend accepted page limits up to 5,000 rows;
- incremental scan already skipped metadata parsing for unchanged `(size, mtime)` files, but persistence still inserted every seen path into a temporary SQLite table and rewrote `last_seen_at` for the whole seen set;
- Local Library artwork resolution performed one cache SQLite lookup per row before resolving the item;
- a no-cover result was not persisted, so an unchanged file could be reparsed on later page loads;
- embedded artwork probing in the row cache path was MP3-specific despite v0.13's format adapter registry;
- Yandex track filtering/sorting was recomputed from the full cached collection on rebuild/keystroke, including the empty-query/original-order case;
- Yandex search had no debounce;
- Yandex list images did not bound decode dimensions.

Historical closed PR #22 was reviewed only as prior evidence. Its changes were not cherry-picked blindly; each retained idea was adapted to the current v0.13 architecture.

## Local Library

### Cache-first activation

Opening Local Library now loads roots and the first SQLite page only. A filesystem scan is an explicit Scan action. Normal navigation and application startup do not traverse configured music roots.

### Bounded pagination

The service enforces a hard maximum of 250 tracks per page independently of Flutter. Search, sort and root filtering remain SQLite predicates applied before `LIMIT/OFFSET`.

The existing Load More contract is retained. Cursor/keyset pagination was intentionally not introduced because v0.14 first measures the 50k synthetic OFFSET path and avoids a semantic migration without evidence.

### Incremental scan persistence

The scanner already had an authoritative pre-scan snapshot keyed by normalized path with size/mtime. v0.14 reuses it to compute:

```text
existing - seen = missing
```

For the current scanner path, persistence receives only:

- new/changed `upserts`;
- explicit `missing_normalized_paths`;
- the successful root scan timestamp.

Unchanged rows are not passed through the write path and their `last_seen_at` values are not rewritten merely to prove the root was scanned. `local_library_roots.last_scanned_at` is the authoritative timestamp for a successful root scan.

The old seen-set persistence path remains only as a compatibility fallback for callers that do not yet provide the missing-path delta.

### Partial-scan safety

Any incomplete filesystem view disables removals for that scan. This includes directory-walk errors and file `stat()` errors. A partial scan may still report/read safe files, but it does not classify unseen rows as deleted.

Symlinks/reparse points remain excluded. Unicode/Cyrillic paths and paths with spaces are covered by the deterministic scan regressions.

## Artwork

Local artwork cache reads are batch-oriented for the current page instead of opening one SQLite cache lookup per row.

A confirmed no-cover result is now cached as `source='none'`. Its fingerprint includes:

```text
file size
mtime
trusted provider external identity
```

Changing the file or trusted provider identity invalidates the negative result. If trusted Yandex artwork later exists in the explicit Yandex cache, a prior negative result does not hide it.

Embedded artwork probing uses the v0.13 `MetadataAdapterRegistry`, so this optimization is not MP3-specific and preserves FLAC/M4A/OGG/Opus/etc. format capability boundaries.

Local row images already used bounded `Image.file(cacheWidth/cacheHeight)`. v0.14 additionally bounds Yandex row and album-card decode dimensions. Full-size metadata-editor artwork remains outside the small-list decode path.

No artwork lookup added by v0.14 performs a metadata-provider network request.

## Yandex workspace

Track search uses a 180 ms debounce. Explicit submit applies the query immediately. The debounce timer is cancelled on dispose and when the view/search scope resets.

For an empty query with original provider order, the existing source collection is returned directly rather than copied/filtered/sorted. Other filter/sort results are memoized only for the current source collection + query + sort and invalidated when any of those inputs change.

The large track list remains `ListView.builder` and uses fixed extent only for the fixed-height Yandex track row.

## Other large workspaces audited

- Matching already requests bounded pages (`50`) and appends only on explicit Load More.
- Coverage already uses bounded page queries (`100`) and a lazy view; its bulk-selection path is explicitly paged rather than materializing the UI as one widget tree.
- Downloads already uses lazy rendering primitives; v0.14 does not redesign its queue/service boundary.
- Controlled Sync remains a plan snapshot and does not gain a new background/job framework.

No persistent Python daemon/job manager is introduced. Existing process bridges remain short-lived explicit operation boundaries.

## Performance harness

`tools/performance_smoke.py` generates deterministic SQLite data programmatically; no giant fixtures are committed.

Default dataset sizes:

```text
1,000 tracks
10,000 tracks
50,000 tracks
```

Synthetic rows include multiple roots, MP3/FLAC/M4A/AAC/OGG/Opus/WAV extensions, Unicode/Cyrillic paths, paths with spaces, repeated artists/albums and deterministic search hits.

The report records representative wall-clock observations for:

- Local Library first-page query;
- search;
- root filtering;
- deep OFFSET page;
- unchanged filesystem scan overhead.

It also records deterministic work metrics such as rows materialized, metadata reads, scan upserts and missing-path count, plus `EXPLAIN QUERY PLAN` output for representative Local Library list/search queries.

Wall-clock numbers are diagnostic evidence, not fragile millisecond acceptance gates. Tight CI assertions are based on deterministic invariants.

## Automated deterministic regressions

Focused Python coverage verifies at least:

- oversized page request is capped at 250;
- unchanged scan performs zero metadata reads and zero upserts;
- partial walk failure cannot remove uncertain files;
- delta persistence does not rewrite unchanged `last_seen_at`;
- negative artwork cache works across the format-adapter boundary and invalidates after file change;
- a fully cached artwork page uses one batch SQLite lookup;
- repeated database initialization is idempotent and remains at the current schema.

Focused Flutter coverage verifies:

- Local Library opens without an automatic scan;
- the first Local Library request is a 250-row page even when total count is 10k;
- a far-away row is not materialized by the first page;
- Yandex search is debounced;
- the Yandex track list retains fixed lazy-row extent.

The existing full v0.11–v0.13 Python/Flutter regression suites remain enabled.

## SQLite and migrations

Core SQLite schema version remains **1.9.0**. v0.14 does not need a schema migration or speculative new indexes.

The existing indexes used by Local Library/provider/matching/coverage/download state are retained. Query-plan output is captured for the changed Local Library hot path; v0.14 does not add an index unless a real query plan and synthetic data demonstrate value.

Fresh initialization and repeated initialization are part of the focused hardening regressions; the existing migration/regression suites remain responsible for historical additive migrations and user-data preservation.

## Startup and failure isolation

v0.14 preserves cache-first startup and does not make Yandex, external metadata providers, proxy/WARP, FFmpeg, fpcalc or a currently missing local root prerequisites for opening the UI.

Failures remain isolated at existing workflow boundaries: Yandex refresh, Local scan, Matching, Variant, Coverage, Download, Metadata Editor, external metadata, conversion, upload and Controlled Sync do not gain a shared failure domain.

Local Library async page loads use a request generation token so an older reload/load-more result cannot overwrite a newer scope.

## CI

The self-hosted Windows workflow contains a separate `performance-regression` job that:

1. checks out the PR head;
2. selects/validates Python;
3. installs MusicArk;
4. clears live Yandex mutation credentials/flags;
5. runs deterministic v0.14 hardening tests;
6. generates the 1k/10k/50k JSON report;
7. uploads it as `musicark-performance-report`.

The Flutter job still requires `flutter analyze`, focused regressions, the full `flutter test` suite and `flutter build windows`.

## Intentionally not optimized

v0.14 does not introduce:

- PostgreSQL or another database;
- a persistent Python daemon/job manager;
- cursor pagination everywhere;
- a new Flutter state-management framework;
- speculative indexes;
- bulk external metadata network lookups on scroll;
- a new Matching/Variant/Coverage truth model.

Any such work requires separate evidence and belongs after the release freeze unless it fixes a concrete release blocker.

## Safety invariants

The following remain true:

```text
Scan rewrites existing audio metadata: NO
Matching rewrites user audio: NO
Coverage rewrites user audio: NO
Normal navigation scans filesystem: NO
Normal scrolling performs metadata network lookup: NO
Performance optimization changes Matching truth: NO
Performance optimization changes Coverage truth: NO
Performance optimization weakens upload duplicate protection: NO
Performance optimization changes source audio during conversion: NO
Partial failed scan deletes uncertain files: NO
CI mutates real Yandex account: NO
```

## Known limitations

- The performance datasets are synthetic and are intended to expose algorithmic/materialization regressions, not to claim exact timing for every user's disk, CPU or media-tag distribution.
- Filesystem scan still necessarily walks configured roots; v0.14 removes unnecessary metadata parsing/database writes, not the O(N) directory traversal required to discover additions/removals.
- `OFFSET` pagination remains in Local Library unless the 50k report demonstrates a real bottleneck worth changing.
- Download queue retrieval retains its existing bounded service contract; v0.14 does not introduce a new job-store pagination architecture.
- Installer, auto-update, GitHub feedback UI and production packaging are explicitly v0.15.0 scope.
