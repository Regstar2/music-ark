# MusicArk v0.10.0 — Yandex Upload Feasibility

## Final milestone result

v0.10.0 is complete. The feasibility question was resolved by a successful direct-Python live proof; the earlier `BLOCKED` conclusion from intermediate research is superseded by the final live result.

Confirmed end-to-end sequence:

```text
Python
  -> Stage 1 HTTP 200
  -> Stage 2 HTTP 201
  -> target playlist read-back
  -> verified=true
  -> ambiguous=false
  -> attemptsUsed=1
```

This is the protocol evidence promoted into production architecture by v0.11.0.

## Confirmed Stage 1 contract

```text
POST https://api.music.yandex.net/loader/upload-url
```

Query parameters:

```text
uid=<authenticated account uid>
playlist-id=<uid>:<playlist kind>
path=<filename only>
```

The successful direct-Python proof did **not** send `visibility` and did **not** require:

- Authorization;
- OAuth header;
- Cookie;
- browser session credentials;
- Chromium/Electron.

The successful HTTPX configuration was:

```text
http1=True
http2=True
trust_env=False
follow_redirects=False
```

The observed Stage 1 success response included:

```text
poll-result
post-target
ugc-track-id
```

## Confirmed Stage 2 contract

Stage 2 is:

```text
POST <dynamic post-target returned by Stage 1>
```

with multipart field:

```text
file=<local MP3>
```

The successful live response was HTTP 201. The proof did not require Authorization, OAuth, Cookie or copied Yandex API session headers on Stage 2.

A preceding research attempt using `requests` ended with a connection reset and was not proof that the server had rejected the file. This observation is why the v0.11.0 production design treats Stage 2 network errors as delivery uncertainty and does not retry automatically.

## Read-back proof

After the HTTP 201 Stage 2 response, the target Yandex playlist was read back. The uploaded UGC track was confirmed in one bounded read-back attempt:

```text
verified=true
ambiguous=false
attemptsUsed=1
```

The final successful direct-Python proof is the source of truth when older research hypotheses conflict with it.

## Research tooling retained

The feasibility tools remain protocol evidence and regression reference, including:

```text
tools/yandex_upload_python_composite_live_poc.py
tools/yandex_upload_*.py
```

Production code must not import from `tools/`.

The old `experimental_yandex_upload` compatibility surface remains separate from the v0.11.0 production mutation so existing scripts cannot silently start uploading files.

## What v0.10.0 did not ship

v0.10.0 was still a feasibility milestone. It did not provide the normal production Local Library upload workflow, production result/audit model, production target validation or user-facing upload dialog. Those belong to v0.11.0.

No SQLite migration, release, installer or bulk upload queue was introduced by v0.10.0.
