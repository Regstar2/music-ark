# v0.3-yandex-scan

## Цель

Научиться получать данные из Яндекс Музыки и сохранять их в универсальной модели MusicArk.

## Главный результат версии

MusicArk умеет авторизоваться в Яндекс Музыке, получать данные аккаунта, лайкнутые треки и пользовательские плейлисты, а затем сохранять их как универсальные provider-данные.

Яндекс Музыка используется как первый реальный provider, но не становится центром архитектуры.

## Используемая библиотека

Для доступа к Яндекс Музыке в этой версии используется неофициальная Python-библиотека:

```text
yandex-music
```

Проект библиотеки:

```text
MarshalX/yandex-music-api
```

Рекомендуемая pinned-зависимость для этой версии:

```text
yandex-music==3.0.0
```

Установка:

```bash
pip install yandex-music==3.0.0
```

Важно:

- библиотека неофициальная;
- библиотека работает с недокументированным API Яндекс Музыки;
- API может измениться без предупреждения;
- версия библиотеки должна быть зафиксирована, чтобы поведение сканера не менялось случайно;
- все объекты библиотеки должны быть изолированы внутри [[yandex-music-provider]];
- [[core]] не должен зависеть от Python-библиотеки, её DTO или структуры ответов;
- данные из библиотеки должны преобразовываться в универсальные модели MusicArk.

## Архитектурное решение по Python-библиотеке

Основное приложение MusicArk разрабатывается на Kotlin/JVM.

Python-библиотека `yandex-music` используется в `v0.3-yandex-scan` как изолированный provider-sidecar / CLI-helper для сканирования данных Яндекс Музыки.

Python-часть отвечает только за:

- авторизацию по токену;
- проверку аккаунта;
- получение лайкнутых треков;
- получение пользовательских плейлистов;
- получение информации о треках;
- сохранение raw responses;
- экспорт нормализованных provider-данных в стабильный JSON-формат.

Python-часть не должна:

- содержать доменную модель MusicArk как источник истины;
- напрямую зависеть от UI;
- напрямую выполнять sync-операции;
- выполнять скачивание треков;
- менять локальную библиотеку;
- хранить токен в репозитории;
- записывать данные в базу в обход Kotlin storage-слоя;
- протаскивать объекты библиотеки `yandex-music` за пределы [[yandex-music-provider]].

Kotlin-часть отвечает за:

- запуск scanner-команды или чтение подготовленного JSON;
- чтение нормализованного JSON;
- валидацию структуры;
- преобразование данных в универсальные модели:
  - `ProviderTrack`;
  - `ProviderPlaylist`;
  - `TrackSource`;
- запись результата в [[storage]];
- запись событий в [[history-audit-log]].

Граница между Python scanner и Kotlin core должна быть стабильной и явно документированной.

Python-объекты библиотеки `yandex-music` не должны протекать в [[core]], [[providers]], [[storage]] или будущий UI.

## Контракт обмена данными

Python scanner должен экспортировать данные в стабильный JSON-формат.

JSON-контракт должен быть версионирован.

Минимальные типы экспортируемых данных:

- account info;
- liked tracks;
- playlists;
- playlist tracks;
- raw responses metadata;
- scan metadata.

Пример верхнего уровня JSON:

```json
{
  "schemaVersion": 1,
  "provider": "yandex_music",
  "scannedAt": "2026-04-30T00:00:00Z",
  "account": {
    "providerUserId": "example-user-id",
    "displayName": "Example User"
  },
  "likedTracks": [],
  "playlists": [],
  "rawResponses": []
}
```

Важно:

- `schemaVersion` обязателен;
- `provider` должен быть равен `yandex_music`;
- даты должны храниться в ISO-8601;
- provider-specific ID не должен становиться глобальным ID трека MusicArk;
- raw responses должны храниться отдельно от нормализованных моделей;
- токены и приватные auth headers не должны попадать в JSON.

## Входит

- авторизация по токену;
- подключение Python-библиотеки `yandex-music` (`MarshalX/yandex-music-api`) внутри изолированного [[yandex-music-provider]];
- фиксация версии Python-зависимости;
- проверка аккаунта;
- сканирование лайкнутых треков;
- сканирование пользовательских плейлистов;
- получение информации о треках;
- сохранение raw responses;
- экспорт нормализованных provider-данных в JSON;
- преобразование данных Яндекса в `ProviderTrack`;
- преобразование плейлистов в `ProviderPlaylist`;
- создание [[track-source]] типа `yandex_music`;
- запись результата в [[storage]];
- запись события скана в [[history-audit-log]];
- документация JSON-контракта между Python scanner и Kotlin storage/import layer;
- тесты для маппинга и повторного скана.

## Не входит

- скачивание треков;
- локальная библиотека;
- сопоставление с локальными файлами;
- синхронизация;
- загрузка пользовательских треков;
- GUI;
- Android;
- torrent support;
- metadata editor;
- массовые изменения плейлистов;
- восстановление коллекции;
- использование Яндекс Музыки как глобального источника истины для всей архитектуры.

## Хранение токена

Токен Яндекс Музыки нельзя хранить в репозитории.

Запрещено:

- хардкодить токен;
- добавлять токен в fixtures;
- добавлять токен в документацию;
- логировать токен;
- передавать токен в Codex-промтах;
- сохранять токен в raw responses.

Допустимые источники токена для локальной разработки:

- переменная окружения;
- локальный `.env`;
- `local.properties`;
- локальный config-файл, добавленный в `.gitignore`;
- безопасное хранилище платформы в будущих версиях.

Рекомендуемые переменные для локальных integration-тестов:

```properties
YANDEX_MUSIC_TOKEN=
YANDEX_MUSIC_EXPECTED_MIN_TRACKS=100
YANDEX_MUSIC_EXPECTED_FIRST_TRACK_ID=
YANDEX_MUSIC_EXPECTED_FIRST_TRACK_TITLE=Courtesy Call
YANDEX_MUSIC_EXPECTED_FIRST_TRACK_ARTIST=Thousand Foot Krutch
```

Если `YANDEX_MUSIC_TOKEN` не задан, integration-тесты должны пропускаться, а не падать.

## Raw responses

Raw responses нужны для отладки и будущего анализа изменений API.

Raw responses должны сохраняться безопасно.

Требования:

- raw responses не должны содержать токены;
- raw responses не должны содержать приватные auth headers;
- raw responses должны быть связаны с provider scan event;
- raw responses должны иметь timestamp;
- raw responses должны иметь тип:
  - account;
  - liked_tracks;
  - playlists;
  - playlist_tracks;
  - track_details;
- raw responses должны быть доступны для отладки;
- формат хранения должен позволять пересобрать маппинг без повторного запроса к API.

Если raw response содержит лишние чувствительные поля, они должны быть удалены или замаскированы перед сохранением.

## Нормализация данных

Данные Яндекс Музыки должны быть преобразованы в универсальные provider-модели.

Минимально нужны:

- `ProviderTrack`;
- `ProviderPlaylist`;
- `TrackSource`.

`ProviderTrack` должен содержать:

- provider id;
- provider track id;
- provider album id, если есть;
- title;
- artists;
- album title, если есть;
- duration;
- explicit flag, если доступен;
- availability status, если доступен;
- raw provider payload reference;
- source type `yandex_music`.

`ProviderPlaylist` должен содержать:

- provider id;
- provider playlist id;
- title;
- owner info, если доступно;
- track ids или track references;
- visibility, если доступна;
- raw provider payload reference;
- source type `yandex_music`.

`TrackSource` для Яндекс Музыки должен иметь тип:

```text
yandex_music
```

Provider-specific ID нельзя использовать как глобальный ID трека MusicArk.

## Повторный скан

Повторный скан не должен ломать базу.

Требования:

- повторный скан должен обновлять provider-данные;
- дубли не должны бесконечно размножаться;
- старые raw responses должны либо версионироваться, либо заменяться по понятному правилу;
- scan event должен записываться каждый раз;
- ошибки частичного скана должны быть явно видны;
- если часть данных не получена, это не должно уничтожать уже сохранённую валидную информацию.

Поведение повторного скана должно быть покрыто тестами.

## CLI-команды

Возможные CLI-команды:

```text
musicark yandex auth-check
musicark yandex scan-likes
musicark yandex scan-playlists
musicark yandex scan-all
```

Команды могут быть реализованы как Kotlin CLI, который вызывает Python scanner, либо как отдельные developer-команды для v0.3.

Главное требование: CLI не должен превращаться в основной слой архитектуры.

CLI — это интерфейс запуска, а не место для доменной логики.

## Критерии готовности

Версия считается готовой, если:

- выбранная библиотека зафиксирована в документации;
- Python-зависимости описаны в отдельном dependency-файле;
- токен можно сохранить и использовать без попадания в Git;
- приложение или scanner получает информацию об аккаунте;
- приложение или scanner получает список лайкнутых треков;
- приложение или scanner получает список пользовательских плейлистов;
- данные Яндекс Музыки преобразуются в универсальные provider-модели;
- данные сохраняются в базе через [[storage]];
- raw response можно посмотреть для отладки;
- повторный скан не ломает базу;
- scan event записывается в [[history-audit-log]];
- граница обмена данными между Python scanner и Kotlin core описана в документации;
- объекты `yandex-music` не используются напрямую в [[core]];
- unit-тесты не требуют реального аккаунта Яндекс Музыки;
- integration-тесты пропускаются, если токен не задан.

## Тесты

Для этой версии нужны тесты там, где появляется логика.

Минимально полезные unit-тесты:

- маппинг Yandex track JSON в `ProviderTrack`;
- маппинг Yandex playlist JSON в `ProviderPlaylist`;
- создание `TrackSource` типа `yandex_music`;
- provider-specific ID не используется как глобальный MusicArk track ID;
- повторный импорт не создаёт дубли;
- raw response сохраняется без токена;
- ошибка отсутствующего токена обрабатывается явно;
- ошибка невалидного токена обрабатывается явно;
- ошибка изменения структуры ответа не приводит к тихой порче данных.

Integration-тесты:

- запускаются только если задан `YANDEX_MUSIC_TOKEN`;
- проверяют авторизацию;
- проверяют получение аккаунта;
- проверяют получение лайкнутых треков;
- проверяют минимальное количество треков, если задано;
- проверяют первый трек:
  - `Courtesy Call`;
  - `Thousand Foot Krutch`;
- если `YANDEX_MUSIC_EXPECTED_FIRST_TRACK_ID` не задан, могут вывести фактический ID первого трека в безопасный лог.

Обычный тестовый прогон не должен требовать сети и реального аккаунта.

## Риски

- сломанный или устаревший API;
- неправильное хранение токена;
- неполные данные;
- изменения структуры ответа;
- слишком много запросов;
- runtime-зависимость от Python в desktop-приложении;
- несовместимость версий Python-библиотеки;
- необходимость версионировать JSON-контракт между Python scanner и Kotlin core;
- риск случайно протащить Yandex-specific DTO в [[core]];
- риск сделать Яндекс Музыку центром архитектуры;
- риск сохранить приватные данные в raw responses;
- риск получить rate limits или временные ограничения аккаунта.

## Решение

Изолировать всю Яндекс-специфику внутри [[yandex-music-provider]].

Использовать Python-библиотеку `yandex-music` только как изолированный scanner/provider-sidecar.

[[core]] должен получать уже нормализованные данные, а не голые объекты библиотеки.

Граница между Python scanner и Kotlin core должна проходить через стабильный JSON-контракт.

Provider-specific ID Яндекс Музыки должен оставаться provider-specific ID, а не становиться глобальным идентификатором MusicArk.

Иначе потом каждый метод в проекте будет пахнуть Яндексом, а это не архитектура, это ароматическая катастрофа.
