# MusicArk v0.8.2 — Local Metadata Editor & Yandex Metadata Import

> The implementation branch is named `v8.2.0` exactly as requested. Package progression remains `0.8.2`; schema progression is now `1.8.4` after the follow-up content-label and variant-acceptance migrations.

## Product goal

v0.8.2 repairs metadata of existing user-owned local MP3 files without turning fuzzy similarity into trusted identity. The editor is the only normal application path that is allowed to modify an already indexed user audio file.

## Metadata versus identity

`Apply metadata` copies only selected, non-empty Yandex metadata and artwork. The file is transactionally rewritten, re-indexed, re-hashed and targeted Matching is refreshed. It does **not** create `EXACT_ID`.

`Apply + Bind` performs the same explicit write and additionally persists the user-confirmed relation:

- provider: `yandex_music`;
- external/local IDs: the selected Yandex Track and edited local file;
- method: `exact_id`;
- confidence: `1.0`;
- reason: `user_confirmed`.

Trusted provenance is embedded only for this explicit bind. Normal metadata-only edits preserve an existing provenance frame set and never fabricate one. Reserved MusicArk/Yandex provenance TXXX frames are read-only in Advanced Tags. On a fresh Local Library index, validated embedded provenance is an exact candidate, so identity survives DB deletion and file renaming.

## Safety model

For the MP3 write adapter the pipeline is:

1. create a same-directory temporary copy;
2. mutate ID3 frames on the copy;
3. write/replace front-cover artwork on the copy;
4. validate the MPEG stream;
5. read ID3 back;
6. `os.replace()` the original atomically;
7. re-index only the edited file;
8. recompute SHA-256 only for that file;
9. targeted Matching refresh plus safe fingerprint rebase for unrelated previously-fresh automatic rows.

If an error happens before the atomic replace, the original file is untouched. MusicArk does not transcode the audio stream.

## Metadata coverage

The MP3 adapter supports title, subtitle, version, multiple artists, album, multiple album artists, track/total, disc/total, release date/year, genres, ISRC, publisher, label, copyright, composer, lyricist, BPM, comment, grouping, lyrics, explicit flag, front artwork, standard text frames and custom TXXX text frames.

Ordinary Basic Editor saves update only requested frames on a copied file. Unknown/custom frames omitted from the request are retained.

## Artwork

Local Library uses a disk cache and passes file paths to Flutter, not large base64 blobs. Embedded artwork has priority. A cached Yandex cover may be used only for a confirmed identity; Local Library rows never trigger background Yandex requests. Flutter decodes list thumbnails with `cacheWidth/cacheHeight`.

The Yandex Library track snapshots additionally keep a public provider artwork URL derived from the Track/Album DTO. That URL contains no authentication material and is used only for lazy row artwork rendering in the Yandex Music tab. Old offline snapshots without the field continue to render the normal artwork placeholder until the provider collection is refreshed.

## Yandex metadata lookup

Search/full-track lookup is executed only in the backend using the existing authenticated Yandex provider boundary. The token stays in the OS credential store. Flutter receives sanitized DTO data and cached artwork paths, never Authorization headers, cookies, direct download links or signed media URLs.

## Yandex Library playback and inline marks

The Yandex Music tab now exposes the same practical media controls as the local library:

- each track row has cover artwork when Yandex supplies it;
- each row has a built-in **Воспроизвести** action;
- the existing app-level **ОРИГИНАЛ / ЦЕНЗУРА** mark is visible and editable directly on the row;
- the separate Yandex content-label management dialog remains available as a bulk/overview path.

Playback deliberately does not send a protected or signed provider media URL to Flutter. The backend uses the authorized Yandex download boundary to prepare the requested track in `.musicark/playback/yandex`, then returns only the local cache path to the existing `media_kit` player. Playback cache files are not indexed into Local Library, do not create Matching identities, and do not change Coverage. Replaying the same track can reuse the private cache through the existing download-provider collision/validation path.

The current Yandex desktop page still owns a fixed-width inner sidebar and desktop-oriented row controls. The application shell therefore preserves a minimum 920 px Yandex workspace. When the outer application window is narrower, that workspace becomes horizontally scrollable instead of letting nested `ListTile` rows collapse into invalid trailing constraints. This is a stabilization safeguard for v0.8.2; a future compact/responsive Yandex layout may replace it without changing provider or playback boundaries.

## Format adapters

The editor is format-adapter based. MP3/ID3 is the first full read/write implementation. Other formats remain read-only in the v0.8.2 UI until their transactional adapters are implemented.

## Non-goals

- no automatic tag correction during Scan;
- no automatic fuzzy-to-Exact promotion;
- no library-wide mass rewrite;
- no audio transcoding;
- no token/protected URL persistence in files;
- no Yandex request per Local Library row.

## Follow-up UX and metadata fixes

- entering Local Library scans configured roots once on every tab activation, then renders the fresh index;
- local tracks and cached Yandex identities can receive app-level **ОРИГИНАЛ / ЦЕНЗУРА** marks; see `[[content-labels]]`;
- Yandex metadata search exposes separate title and artist fields;
- Apply Metadata and Apply + Bind show a persistent success summary in addition to the transient SnackBar;
- ID3 Comment no longer renders a Mutagen/Python list representation, and likely CP1251-as-Latin-1 mojibake is repaired for display without background tag rewriting;
- filename is explicitly editable; Yandex Compare proposes `Artist - Title.ext`, and selected filename changes use a same-directory safe rename with collision checks and single-file reindex.

## Matching comparison follow-up

The Matching detail dialog now uses a three-column comparison table: `Parameter | Yandex Music | Local file`. Title, artist, album, duration, content label and local location are aligned row-by-row. Both provider and local subjects can receive the existing `ОРИГИНАЛ / ЦЕНЗУРА` app-level labels directly from this dialog.

All user-facing Matching and Variant labels on this screen are Russian. Internal status codes remain unchanged at the backend boundary.

For `altered`, `different_version` and `uncertain`, the user can explicitly choose **«Эта версия меня устраивает»**. This decision is stored separately from the analyzer result; see `[[variant-acceptance]]`. The raw `track_variant_results.status` is not changed. Coverage / Controlled Sync consider a decision valid only while it still matches the exact analysis evidence, and then stop surfacing that recording as an unresolved variant review blocker.


Neither migration modifies user audio.
