# MusicArk v0.11.1 — Bulk Upload, Recovery Sync & Explicit Scope Context

Status: implementation branch / Draft PR. No release, tag or installer is created by this version work.

## Goal

v0.11.1 extends the proven v0.11.0 single-track Yandex upload primitive into a controlled collection-recovery workflow. `YandexSingleTrackUploadService` remains the only one-file upload primitive. Batch and Sync code do not implement a second upload transport.

## Upload invariants inherited from v0.11.0

Every file upload still enforces MP3-only input, `local_file_id` instead of an arbitrary UI path, owned playlist verification, explicit mutation and rights confirmations, no OAuth/cookie injection into Stage 2 requests, Yandex-only signed targets, redirects disabled, no Stage 2 automatic retry, bounded read-back, `delivery_unknown` for uncertain delivery, and sanitized result/audit/log boundaries.

## Batch upload

`YandexBatchUploadService` accepts a bounded list of local file IDs and a destination playlist kind. It executes sequentially with `concurrency = 1` and calls `YandexSingleTrackUploadService.upload_track(...)` for every safe item.

One failed item does not stop later items. `delivery_unknown`, `processing` and `ambiguous` are separated from hard failures and are never added to the automatic retry list. Cancellation is cooperative between tracks: the currently executing single-track primitive completes, then the remaining items are cancelled/not started.

## Duplicate protection

`yandex_upload_mappings` persists `local_file_id`, destination playlist kind, returned UGC track ID when known, result state and upload/verification timestamps. Before a repeated upload MusicArk reads the target playlist back. A verified mapping still present is skipped as already uploaded. An uncertain mapping is not automatically retried. A stale verified mapping requires an explicit recovery upload path. Filename/title matching is not used as the identity mechanism.

## Managed MusicArk playlists

Stable roles are persisted as `role -> owned playlist kind`:

| Role | Default title | Purpose |
| --- | --- | --- |
| `censored` | `ЦЕНЗУРА` | confirmed censored provider track → confirmed local original |
| `uploaded` | `ЗАГРУЖЕННЫЕ ТРЕКИ` | default manual single/bulk target |
| `unavailable` | `НЕДОСТУПНЫЕ` | unavailable provider track → local replacement |

Playlist title is discovery/UI metadata, not identity. Configured kinds are re-read and ownership checked before use. Exact-title discovery adopts only one unambiguous owned playlist. Multiple exact-title matches require user selection. Repeated ensure does not create duplicates.

### Playlist creation capability

Production creation remains fail-closed until a manual live proof succeeds. During this implementation `PLAYLIST_CREATE_LIVE_PROVEN = False`, so the production UI supports assigning existing owned playlists and does not assume playlist creation works.

If creation is later explicitly proven, managed playlists are private-only and creation still requires user confirmation.

## Playlist API research utility

`tools/yandex_playlist_research.py` is manual-only and requires:

```text
MUSICARK_YANDEX_PLAYLIST_LIVE=1
```

It proves, using the pinned `yandex-music==3.0.0` dependency and the authenticated user's own data: owned playlist revision read, private `MusicArk v0.11.1 TEST` creation, read-back, insertion of a real available Yandex track, membership read-back, cleanup, and unavailable-provider-track insertion only when a real cached fixture exists. It never guesses an unavailable track ID.

The output is sanitized: method/result, safe HTTP status, playlist kind, track ID and exception class may be reported; token, UID, cookies, request headers, signed URLs and raw responses are excluded.

### Research result for this implementation

No real Yandex playlist mutation was run automatically or in CI.

- Can create playlist: **not live-tested; production capability remains disabled**.
- Can insert available track: **not live-tested**.
- Can insert unavailable provider track: **not live-tested**. With no real fixture the tool reports `not_tested_no_fixture`.

The existence of library methods is not treated as proof of a production capability.

## Provider availability and recovery

Provider availability is independent of local Coverage. For example, `coverage = covered` together with `providerAvailability = unavailable` is valid and is a preferred recovery candidate.

Availability states are typed as `available`, `unavailable`, `unknown`. Explicit provider `available=false` is an unavailable signal. Membership disappearance by itself is not classified as unavailable; last-known metadata is retained and the item moves to review/unknown unless provider evidence proves unavailability.

Lightweight history keeps last-known title/artists/album/artwork, last-seen/available timestamps, unavailable-since and last-known collections. Raw provider responses are not copied into history.

Recovery states include `healthy`, `unavailable_local_available`, `unavailable_local_missing`, `censored_original_available`, `censored_original_missing`, `unavailable_needs_review`, and `censorship_needs_review`.

Censorship auto-recovery is deliberately strict: provider content label must be explicitly `censored`, matched local content label explicitly `original`, and the local file must be an available MP3. Variant states such as `altered`, `different_version` or `uncertain` alone never prove censorship and remain review-only.

If a previously unavailable provider track becomes available again, the active unavailable state is removed on refresh and an audit transition is retained. MusicArk does not automatically delete a previously uploaded UGC replacement.

## Controlled Sync

v0.11.1 adds production operation type `UPLOAD_LOCAL_TO_YANDEX`. Historical `UPLOAD_CANDIDATE` semantics are preserved.

For unavailable recovery the planner requires provider-unavailable + local available MP3 + configured managed `unavailable` role. For censorship recovery it requires explicit provider censored + explicit matched local original + local MP3 + configured managed `censored` role.

The planner remains read-only. Apply revalidates plan staleness, current recovery state, local file identity/existence/format, content labels and managed playlist ownership. Downloads use the existing download service. Uploads use the batch coordinator, which in turn uses the existing single-track service. Sync performs no direct upload HTTP requests.

Upload operations require a fresh rights confirmation in the Apply dialog. A download folder is required only when pending download operations exist. Upload-only plans can be applied without a download target.

## UI

v0.11.1 adds a reusable responsive `ScopeContextBar`, direct row upload action beside Play/Edit, Local Library selection by `local_file_id`, select-all-visible/clear/bulk toolbar, batch upload summary and real item-count progress, managed-playlist configuration by names, a recovery/unavailable section with filters, and a Sync confirmation that displays download and upload counts separately plus upload roles.

`delivery_unknown` is presented as a manual playlist-check state and is never included in blind “retry errors”.

All new product strings are exposed through the RU/EN v0.11.1 localization facade.

## Database

Schema version moves from `1.8.4` to `1.9.0` with an additive, idempotent, forward-only migration. Existing user tables are not destructively rebuilt.

New tables:

- `managed_yandex_playlists`;
- `yandex_upload_mappings`;
- `provider_track_availability_history`;
- `yandex_upload_batches`;
- `yandex_upload_batch_items`.

## Security and audit

New audit events cover batch start/finish/cancel, managed playlist create/adopt, provider unavailable/available-again and Sync upload results. Safe IDs, roles, kinds and result states may be stored. Token, UID, Authorization, Cookie, signed upload/poll URLs, raw HTTP bodies and filesystem paths are excluded from upload/batch/Sync audit and Flutter-visible upload state.

## Known limitations

v0.11.1 does not implement format conversion/transcoding, parallel upload workers, background daemon, automatic replacement inside original user playlists, automatic deletion of source tracks, automatic cleanup when an original returns, installer, auto-update, mobile port or release packaging.

Playlist creation remains disabled in production until the manual live proof is actually performed and reviewed.
