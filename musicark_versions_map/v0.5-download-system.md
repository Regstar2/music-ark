# v0.5-download-system

## Цель

Вынести получение файлов в отдельный универсальный слой [[download-system]].

Это нужно сделать до реализации скачивания из Яндекс Музыки, чтобы потом можно было добавить [[torrent-download-provider]], HTTP, ручной импорт и другие способы без перелома архитектуры.

## Главный результат версии

Появляются [[download-task]], [[download-provider]], очередь задач и общий механизм обработки загрузок.

## Входит

- модель [[download-task]];
- интерфейс [[download-provider]];
- очередь загрузок;
- статусы задач;
- прогресс задач;
- обработка ошибок;
- отмена задачи;
- повтор failed-задачи;
- связь [[download-task]] -> [[track-source]];
- связь [[download-task]] -> [[local-audio-file]];
- базовый [[local-import-provider]];
- запись событий в [[history-audit-log]].

## Не входит

- реальное скачивание из Яндекс Музыки;
- torrent-загрузки;
- GUI-очередь загрузок;
- сложная параллельная загрузка.

## Критерии готовности

- можно создать задачу загрузки;
- задача имеет статус и прогресс;
- можно выполнить local import через общий механизм;
- ошибка задачи сохраняется;
- результат задачи связывается с [[local-audio-file]];
- интерфейс [[download-provider]] не зависит от Яндекс Музыки.

## Возможные CLI-команды

```text
musicark download task-create
musicark download queue
musicark import file "D:/Music/track.mp3"
```

## Важное архитектурное решение

[[sync-planner]] в будущем должен создавать [[download-task]], а не вызывать скачивание напрямую.

Правильный поток:

```text
[[sync-planner]]
-> [[download-task]]
-> [[download-system]]
-> [[download-provider]]
-> [[local-audio-file]]
```

## Риски

- сделать систему слишком сложной до первого реального downloader;
- привязать [[download-task]] к Яндекс Музыке;
- не предусмотреть будущий [[torrent-download-provider]].

## Решение

Сделать минимальный, но универсальный механизм.

Torrent пока не реализуется. Он просто учитывается архитектурно. Вот так и надо обращаться с будущими фичами: оставить дверь, а не строить целый вокзал.
