# v0.15.0 — Installer, Auto-Update, Feedback & Packaging

## Goal

Turn the v0.14 desktop codebase into a distributable Windows application without reopening product feature scope.

v0.15.0 is release engineering only:

```text
Flutter Windows release
+ frozen MusicArk backend runtime
+ per-user installer / portable ZIP
+ update manifest / integrity verification
+ explicit update UX
+ GitHub feedback entry points
+ distribution tests and documentation
```

No new Matching, Variant, Coverage, Download, Sync, Metadata, Yandex upload or provider semantics belong in this milestone.

## Version source

`VERSION` is the canonical release value. `tools/check_version_consistency.py` fails when release-facing mirrors drift:

- `pyproject.toml`;
- `src/musicark/__init__.py`;
- `ui/musicark_ui/pubspec.yaml`;
- `ui/musicark_ui/lib/app_info.dart`.

v0.15.0 keeps the core SQLite schema at `1.9.0`.

## Standalone backend runtime

Installed MusicArk must not require a developer checkout, `.venv`, or separately installed Python.

`musicark.runtime_cli` is frozen by PyInstaller into a restricted runtime. It accepts only:

```text
--version
-m <approved MusicArk bridge module> ...
```

It is not a general Python shell. The packaged layout names the executable `.venv/Scripts/python.exe` only for compatibility with older Flutter bridge discovery code. The executable itself is a frozen MusicArk runtime.

Legacy bridge `--base-dir` values are rewritten inside the frozen runtime to the per-user MusicArk data root before any backend service is invoked. On Windows the default is:

```text
%LOCALAPPDATA%\MusicArk
```

Therefore mutable database/cache/configuration state is not stored in the installation directory and survives ordinary application upgrade/uninstall.

The package contains minimal sentinel paths used only by old Flutter repository-root detection. They are not an executable source checkout.

## Windows packaging

`tools/package_windows.ps1` builds:

- Flutter Windows release;
- frozen one-directory MusicArk runtime;
- standalone staged application;
- portable `MusicArk-<version>-win-x64.zip`;
- `SHA256SUMS.txt`;
- Inno Setup installer when `ISCC.exe` is available.

Release installer source:

```text
packaging/windows/MusicArk.iss
```

The installer is per-user and defaults to:

```text
%LOCALAPPDATA%\Programs\MusicArk
```

It supports in-place upgrade through a stable Inno `AppId`. Uninstall removes application files only. MusicArk data under `%LOCALAPPDATA%\MusicArk` and external applications such as Cloudflare WARP are intentionally not silently removed.

`-SkipInstaller` exists only for packaging smoke environments where Inno Setup is unavailable. A public release must not claim installer verification unless the installer was actually compiled and tested.

## Update contract

The application uses a strict JSON manifest (`schemaVersion = 1`) containing:

- channel;
- semantic version;
- publication timestamp;
- installer HTTPS URL;
- exact installer SHA-256;
- exact installer byte size;
- plain `.exe` file name;
- optional release-notes URL.

Update URLs fail closed unless they use HTTPS on approved GitHub/GitHubusercontent hosts. Redirects are bounded and every redirect target is revalidated.

Update flow:

```text
check
  -> read/validate manifest only
prepare
  -> download installer
  -> verify exact size
  -> verify exact SHA-256
  -> atomic promotion from .part
apply
  -> require explicit confirmation
  -> re-read prepared metadata
  -> re-verify file
  -> launch installer
```

Checking never installs anything. Downloading never launches anything. A network failure, malformed manifest, untrusted redirect, size mismatch or hash mismatch fails closed.

The manifest endpoint is configurable through `MUSICARK_UPDATE_MANIFEST_URL`. Until the public release channel is published, update discovery may return an unavailable/network state; this does not block implementation or local distribution validation.

`tools/generate_update_manifest.py` produces a manifest from a real built installer and computes its hash/size rather than trusting hand-written values.

## Feedback

Settings exposes explicit actions for:

- Bug report;
- Feature request.

The links target GitHub Issue Forms. The default public repository URL can be overridden with `MUSICARK_PUBLIC_REPOSITORY_URL` at deployment time.

Automatic diagnostic text is deliberately limited to:

- MusicArk version;
- OS family/release;
- machine architecture.

It excludes tokens, cookies, signed provider URLs, proxy passwords, account identifiers, local music paths and library contents. Users are still instructed to review the report before submitting.

## WARP ownership / uninstall boundary

v0.12 already tracks whether WARP was installed by MusicArk in `network_component_state`.

v0.15 does not silently uninstall WARP from the Windows uninstaller. Even an owned external component may be used by another application after installation. External dependency removal requires a separate explicit user action; application uninstall only removes MusicArk program files.

## UI

Settings now includes an `Updates and feedback / Обновления и обратная связь` card with:

- current/latest version;
- explicit check action;
- update-available/up-to-date state;
- separate Download and Install actions;
- confirmation before installer launch;
- Bug / Feature feedback actions;
- RU/EN presentation.

Automatic check failure is non-fatal and does not prevent Settings from opening.

## Tests / CI

Backend regression coverage includes:

- strict semantic version parsing;
- manifest validation;
- trusted HTTPS host enforcement;
- bounded GitHub redirect path;
- size and SHA-256 verification;
- `.part` failure safety;
- feedback privacy;
- frozen runtime data-root rewrite.

Flutter coverage includes:

- explicit Check -> Prepare -> confirmation -> Apply sequence;
- no install before confirmation;
- feedback actions;
- RU/EN text.

`.github/workflows/v015-distribution.yml` adds focused distribution gates and a standalone package smoke artifact. Installer compilation is attempted only when Inno Setup is actually present and must be reported factually.

## Signing

v0.15 adds no fake code-signing claim. If no trusted Windows signing certificate is configured, artifacts remain unsigned and this must be disclosed in the release checklist/notes. Signing can be added as a release-pipeline credential without changing application semantics.

## Non-goals

- no tag or GitHub Release publication;
- no automatic PR merge;
- no public-repository visibility change;
- no silent self-update;
- no background service;
- no installer-driven database deletion;
- no automatic WARP removal;
- no new product feature milestone.

## Acceptance boundary

v0.15.0 is complete only when the implementation, tests, packaging smoke, documentation and real CI state are recorded. Installer compilation/signing/manual clean-machine validation remain explicit factual gates; they are never inferred from source code alone.
