# future-providers-support

## Цель

Добавить поддержку других музыкальных сервисов через [[providers]] и [[provider-capabilities]].

## Статус

Будущее направление.

Первая версия практически ориентирована на [[yandex-music-provider]], но архитектура должна позволить добавить новые сервисы без переписывания [[core]].

## Возможные провайдеры

- YouTube Music;
- Spotify;
- SoundCloud;
- VK Music;
- Apple Music;
- Deezer;
- другие сервисы.

## Главная идея

Каждый новый сервис добавляется как отдельный провайдер.

Не все сервисы обязаны поддерживать скачивание или загрузку. Возможности каждого сервиса описывает [[provider-capabilities]].

## Входит

- реализация нового provider adapter;
- авторизация конкретного сервиса;
- сканирование библиотеки, если доступно;
- сканирование плейлистов, если доступно;
- импорт provider tracks;
- создание [[track-source]];
- matching через [[matching-engine]];
- отображение возможностей в [[ui]];
- интеграция с [[sync-planner]].

## Не входит по умолчанию

- скачивание из любого сервиса;
- upload в любой сервис;
- обход ограничений сервиса;
- единая логика “все сервисы умеют всё”;
- пиратские источники.

## Критерии готовности для нового провайдера

- провайдер регистрируется в системе;
- capabilities отображаются в UI;
- данные преобразуются в универсальные модели;
- создаются [[track-source]];
- работает matching;
- unsupported-действия не показываются или явно заблокированы;
- ошибки провайдера изолированы от [[core]].

## Риски

- разные сервисы имеют разные ограничения;
- часть API может быть неофициальной;
- некоторые сервисы не дают скачивать файлы;
- разные модели плейлистов;
- разные форматы ID и метаданных;
- сложный matching между сервисами.

## Решение

Не пытаться сделать “единый музыкальный API для всего мира”.

Нужно делать адаптеры с capabilities. Это скучнее, зато честнее. А честная архитектура редко бывает модной, потому что не обещает невозможного за два спринта.
