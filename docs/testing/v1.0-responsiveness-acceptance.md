# v1.0 responsiveness acceptance

This checklist covers the release blocker tracked by GitHub Issue #39. It is evidence for the Windows v1.0 acceptance pass; it does not replace automated tests.

## Target data set

Use the real Windows desktop build with:

- a Yandex Music collection of at least 5,000 tracks;
- a configured Local Library root containing enough files to exercise candidate lookup;
- the same account and local data between baseline and fixed-build measurements.

Record the exact commit SHA and whether the run is a cold first match or an incremental rerun.

## Matching responsiveness

1. Open `Matching`.
2. Start matching.
3. Verify that processed/total progress changes while the run is active.
4. Switch to `Local Library`, `Missing`, `Downloads`, and back to `Matching` while the run is active.
5. Verify that the matching button remains in the running state and the processed/total counter is not reset.
6. Change Light/Dark/System theme while matching is active.
7. Move/resize the window and continue navigation.
8. Wait for matching to finish and verify that the final summary/result table refreshes.

Expected:

- Windows does not mark Music Ark as `Not responding` during ordinary tab/theme interaction;
- tab changes do not start a second matching run;
- the matching page is not recreated merely because the user navigated away;
- progress is monotonic and ends at the provider identity count;
- final matching semantics remain compatible with the existing v0.5 regression suite.

## Large Coverage / Downloads responsiveness

On the first real-Windows acceptance build, the >5k workflow exposed additional failures and therefore the acceptance result remains FAIL/NOT VERIFIED:

- `Missing -> Select all` caused long stalls and the application reached Windows `Not responding`;
- applying a bulk Coverage action above 5,000 selected tracks failed with `invalid_request: Bulk coverage payload is limited to 5000 tracks.`;
- the persistent `Downloads -> Wanted` page could show stale data after changing Coverage actions.

The follow-up fix keeps the backend bulk-request safety boundary, but the UI now sends actions in bounded chunks and performs larger bounded Coverage reads to reduce frozen-runtime process churn. The persistent Downloads page refreshes its current tab whenever it becomes active again.

Retest:

1. Open `Missing` with more than 5,000 filtered missing tracks.
2. Press `Select all` and verify that the application remains interactive while the full filtered selection is collected.
3. Apply `Wanted` (and, if useful, reset/ignored) to the selected set.
4. Verify that no 5,000-track aggregate error is displayed and the action eventually covers the entire selected set.
5. Navigate immediately to `Downloads -> Wanted` and verify that the count/list reflects the new Coverage decisions on entry, without requiring a manual refresh or page recreation.
6. Switch between `Missing`, `Downloads`, and another data page during the workflow and verify that Windows does not report `Not responding`.

## Automated coverage

The blocker adds regression coverage for:

- monotonic matching progress and completion;
- one-time exact-Yandex-ID candidate preloading per matching run;
- preservation of an in-flight `MatchingPage` across navigation;
- a 5,201-track Coverage selection split into bounded bulk-action chunks;
- refresh of the persistent Downloads/Wanted page when it becomes active again.

## Result

- Initial Windows portable build: `BUILT` using Python 3.13 packaging runtime on the tester machine.
- Initial large-library acceptance: `FAIL` — Coverage bulk limit, stale Wanted state and `Not responding` were observed.
- Follow-up fix commit: `NOT VERIFIED` on Windows until a new portable ZIP is built and the retest above is executed.
- Status: `NOT VERIFIED` / release-blocking until the follow-up Windows acceptance passes.
