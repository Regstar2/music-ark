# v0.5.1 — Variant / Altered Track Detection

## Scope

v0.5.1 adds a second verification layer after v0.5 identity matching.

```text
Yandex track + Local track
        ↓
 v0.5 Identity Matching
        ↓ MATCHED / accepted manual link
 v0.5.1 Variant Detection
        ↓
 SAME / ALTERED / DIFFERENT_VERSION / UNCERTAIN / NOT_CHECKED
```

The two questions remain separate:

1. **Identity:** are these objects the same track/work? (`MATCHED / CONFLICT / UNMATCHED` + identity confidence)
2. **Variant:** are they the same recording/version? (variant status + audio evidence)

v0.5 identity statuses and confidence are not replaced or reinterpreted.

## Metadata variant evidence

`MetadataVariantDetector` extracts semantic markers independently from identity normalization. Supported markers include `live`, `remix`, `mix`, `acoustic`, `instrumental`, `remaster`, `remastered`, `radio edit`, `radio version`, `edit`, `extended`, `demo`, `clean`, `explicit`, `censored`, and `uncensored`.

Signals include title, artists, album, duration, provider `explicit`/Yandex `content_warning`, and the local filename as a weak variant hint. Matching normalization continues to preserve semantic words rather than deleting them.

An explicit mismatch is evidence only. It never proves that a local file is censored or uncensored by itself.

## Reference audio

Deep verification requires a trusted reference for the exact provider track ID. `ReferenceAudioResolver` recognizes only the strict existing convention:

```text
yandex_<track_id>.<ext>
yandex-<track_id>.<ext>
```

Example:

```text
.musicark/downloads/yandex/yandex_69046542.mp3
```

An arbitrary number elsewhere in a path is not treated as a Yandex track ID.

### Current tested acquisition contract

The merged code/tests are the source of truth. During an **explicit single-track `variant_run`**, `VariantDetectionService` may invoke the bounded `ReferenceAudioAcquirer` to obtain one exact Yandex reference when no exact local reference is available and acquisition is supported.

This corrects older documentation that broadly stated MusicArk never acquires a reference automatically.

The boundary is strict:

- acquisition belongs only to explicit single-track recording/version verification;
- `variant_run_all_available` remains bounded to pairs with already-resolvable exact references and does not silently download a whole library;
- the cache under `.musicark/downloads/yandex` is not Local Library;
- acquired references are not inserted into `local_audio_files` and do not create `track_links`;
- reference presence never establishes identity matching or Library Coverage;
- ordinary unresolved `UNMATCHED` / `CONFLICT` rows are not promoted by reference acquisition.

## Decoded-audio pipeline

```text
VariantDetectionService
    ↓
MetadataVariantDetector
    ↓
ReferenceAudioResolver / bounded ReferenceAudioAcquirer
    ↓
AudioDecoder abstraction
    ↓
FfmpegAudioDecoder
    ↓ mono / signed-16 PCM / 11025 Hz via pipe
AudioAligner
    ↓ bounded ±15 s coarse energy correlation
SegmentComparator
    ↓ 2.0 s windows / 0.75 s hop
VariantClassifier
```

MP3/FLAC bytes and SHA-256 equality are not used to decide whether recordings are the same. ffmpeg decodes supported formats to one PCM representation. PCM is kept in memory in a compact signed-16 array and is never stored in SQLite.

Segment similarity combines a normalized loudness envelope, compact spectral measurements, zero-crossing rate, and waveform-derivative evidence. Adjacent low-similarity windows are merged into altered regions with start/end/mean/minimum similarity.

## Status policy

### SAME

Requires compatible variant metadata, high decoded-audio similarity, a high median window similarity, few/no low-similarity windows, and no meaningful altered region.

### ALTERED

Used when most of the recording remains strongly consistent but a small number of persistent localized regions diverge. A provider `explicit=true` plus close duration plus localized divergence can add the conservative reason `possible_clean_or_censored_variant`; it is not a guaranteed censorship classification.

### DIFFERENT_VERSION

Used for strong semantic version mismatches (for example Live/Remix/Acoustic/Instrumental/Radio Edit), or when duration/audio divergence is too broad for SAME/ALTERED.

### UNCERTAIN

Used when evidence conflicts, alignment/decode interpretation is unreliable, audio is too short, or the result lies near policy boundaries. Technical errors do not become `DIFFERENT_VERSION`.

### NOT_CHECKED

Used when deep verification has not run, reference audio is absent, or audio verification is unavailable.

False-positive `SAME` is intentionally treated as worse than `UNCERTAIN`.

## ffmpeg dependency

ffmpeg is an optional runtime capability for decoded-audio verification, not a hard application dependency. If it is absent:

- Yandex and Local Library continue working;
- v0.5 matching continues working;
- metadata variant evidence remains available;
- audio verification returns a clear `NOT_CHECKED`/conservative result;
- the UI shows that audio comparison is unavailable.

No silent failure is allowed.

## Database migration

SQLite schema advances forward-only:

```text
1.4.0 → 1.5.0
```

The migration adds `track_variant_results` keyed by `(provider_id, external_id, local_file_id)` with status, metadata evidence, audio similarity, reasons, altered regions, provider/local/reference fingerprints, analyzer version, reference path, and timestamps.

PCM/audio blobs are not stored. Existing Yandex cache, Local Library data, v0.5 `matching_results`, `track_links`, conflicts, and manual decisions remain intact.

## Cache and invalidation

Variant analysis is reused only when all relevant fingerprints and `ANALYZER_VERSION` match. Recompute is triggered by changes to:

- provider metadata relevant to variant analysis, including `explicit` and semantic markers;
- local path/file size/mtime;
- reference path/file size/mtime;
- analyzer version.

Technical failure results are not treated as permanently cacheable. A newly installed decoder can therefore be used without deleting the database.

## Performance boundary

Audio verification is never a Cartesian comparison over the library. It begins only after a v0.5 `MATCHED` identity or manually accepted link. `variant_run_all_available` limits work to pairs for which a strict reference audio file can already be resolved. Each file failure is isolated so it does not abort the batch.

Flutter starts the Python process asynchronously, so decoded-audio work stays Python-side rather than blocking the Flutter event loop or crossing the bridge as PCM.

## Bridge

Added commands:

- `variant_capabilities`
- `variant_summary`
- `variant_run --external-id <id>`
- `variant_run_all_available`
- `variant_result --external-id <id>`
- `variant_results`

`matching_run` remains dedicated to identity matching.

## UI

The existing Matching page gains a secondary variant badge for matched rows:

- `SAME`
- `ALTERED`
- `DIFFERENT VERSION`
- `UNCERTAIN`
- `NOT CHECKED`

The detail dialog keeps separate **Identity** and **Variant verification** sections. Variant details show audio similarity, reasons, altered regions, reference path, decoder availability, and a `Проверить версию` action. `Проверить все доступные` runs the bounded batch over matched pairs with already-resolvable references.

## Tests

Python tests use generated synthetic signals and temporary files, not copyrighted music. Coverage includes identical/copy-like audio, localized silence/tone replacement, large changes, bounded alignment, duration differences, semantic markers, explicit evidence, missing reference/decoder, decode errors, strict Yandex-ID resolution, bounded explicit reference acquisition, cache reuse, local/reference invalidation, and the 1.4→1.5 preservation migration.

Flutter widget tests cover variant badges, NOT CHECKED, Verify Version, decoder-unavailable UI, altered regions, progress state, per-analysis error state, and refresh after verification. Surface-size cleanup uses `addTearDown(...)` inside each widget-test zone.

## Local validation

Run locally:

```powershell
python -m unittest discover -s tests -v
cd ui/musicark_ui
flutter analyze
flutter test
flutter run -d windows
```

Manual real-library validation should include same recording in MP3/FLAC, gain/encoding differences, legally owned clean/explicit variants when available, Radio Edit, Live, Remix, and a copy of test/owned audio with a short region replaced by silence.

The primary quality gate is that an obvious different version must not be automatically shown as `SAME`.

## Safety / limitations

- no external matching, metadata, or fingerprint API;
- bounded explicit single-track reference acquisition only; no library-wide automatic reference download;
- acquired reference cache is not Local Library and is never promoted into matching links;
- no destructive local-file operation;
- no local music modification;
- no censorship claim based on metadata alone;
- no unrestricted dynamic alignment over a collection;
- no PyTorch/TensorFlow/ML stack.
