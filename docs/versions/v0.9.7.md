# v0.9.7 — Large Library Performance

## Goal

Reduce avoidable CPU, disk, SQLite, image-decoding and Flutter rebuild work when MusicArk libraries contain thousands of tracks, without changing Matching, Coverage, Download, Sync or Metadata Editor semantics.

## Changes

### Local Library

- Local Library activation is cache-first. Opening the page no longer starts a recursive filesystem scan automatically; Scan remains an explicit user action.
- UI/backend track pages are bounded to 250 rows. Existing Load More pagination remains the way to request subsequent rows.
- Incremental scanning computes deleted paths from the already loaded file-state snapshot and persists only actual scan deltas instead of inserting every unchanged path into a temporary SQLite table and rewriting `last_seen_at` for every unchanged row.
- Artwork batch lookup reads cache records for the page in one SQLite query instead of opening one SQLite connection per track.
- Files with no embedded/provider artwork receive a fingerprinted negative artwork-cache entry. Unchanged MP3 files without covers are not reparsed every time the page reloads.
- Artwork cache invalidates when file size/mtime or trusted provider identity changes.

### Yandex workspace

- the no-search/original-order track view returns the provider list directly instead of copying/filtering thousands of rows on each relevant rebuild;
- filtered/sorted track results are memoized until source/query/sort changes;
- track search is debounced by 180 ms, while submit applies immediately;
- the track list uses a fixed 72 px item extent for cheaper large-list layout;
- 48 px track artwork is decoded into a bounded 96×96 cache target, and album artwork uses a bounded 512×512 target.

## Safety / non-goals

- SQLite schema remains `1.8.4`;
- no user audio file is deleted, moved, renamed or retagged by these changes;
- Scan still detects new/changed/deleted files when the user explicitly runs it;
- Matching/Variant, Coverage, Downloads and Controlled Sync truth/side effects are unchanged;
- no Yandex mutation, reverse sync or upload behavior is introduced;
- no new dependency is added.

## Regression coverage

Added/updated tests cover:

- negative artwork caching and invalidation after a local file changes;
- scanner propagation of only the missing-path delta while leaving unchanged files untouched;
- hard upper bound for Local Library page materialization;
- cache-first Local Library activation plus explicit Scan;
- debounced Yandex track search and fixed-extent track list.

## Verification status

The GitHub connector cannot execute the local Python/Flutter toolchains. Do not treat the presence of tests as a PASS. Run the repository Python suite, Flutter analyzer/tests and Windows smoke against the final branch head before acceptance.

## Manual large-library smoke

Use a real library around 5,000 tracks and verify:

1. opening/reopening Local Library does not immediately start a filesystem scan;
2. the first page becomes interactive before the full library is materialized;
3. Load More continues with the same search/sort/root selection;
4. a second Local Library reload does not repeatedly parse no-cover MP3 artwork;
5. explicit Scan still finds additions, metadata changes and deletions;
6. Yandex track scrolling remains smooth and search does not rebuild the 5k-row filter on every keystroke;
7. memory does not grow as if every remote cover were decoded at source resolution.
