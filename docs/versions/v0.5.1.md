# MusicArk v0.5.1 — Variant / Altered Track Detection

v0.5.1 is a second analytical layer after accepted v0.5 identity matching. It reports `SAME`, `ALTERED`, `DIFFERENT_VERSION`, `UNCERTAIN`, or `NOT_CHECKED` without changing `MATCHED / CONFLICT / UNMATCHED`.

## Current reference-audio contract

The merged code/tests are the source of truth. `ReferenceAudioResolver` accepts only exact provider-ID references (`yandex_<id>.<ext>` / `yandex-<id>.<ext>`). During an **explicit single-track `variant_run`**, `VariantDetectionService` may invoke the bounded `ReferenceAudioAcquirer` to obtain one exact Yandex reference when no exact local reference is already available and acquisition is supported.

This corrects older documentation that broadly stated that MusicArk never acquires a reference automatically.

The bounded reference mechanism has strict boundaries:

- it belongs only to v0.5.1 recording/version verification;
- it is not a Missing Tracks or download workflow;
- its cache under `.musicark/downloads/yandex` is not Local Library;
- acquired references are not inserted into `local_audio_files` and do not create `track_links`;
- reference presence does not establish identity coverage;
- ordinary unresolved `UNMATCHED` / `CONFLICT` rows are not promoted to matched by reference acquisition.

Batch/deep verification remains conservative and ffmpeg remains optional. Technical/reference failures never imply `DIFFERENT_VERSION`.

## Persistence

Schema v1.5 stores `track_variant_results` with independent provider/local/reference fingerprints and analyzer version. No PCM/audio blobs are stored.

## Safety

Variant analysis does not rename/move/delete/edit user music and does not mutate Yandex likes/playlists. Its bounded explicit reference acquisition is retained as implemented; v0.6 does not expand it into general missing-track acquisition.
