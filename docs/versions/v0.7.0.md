# MusicArk v0.7.0 — Download

## Product contract

v0.7 closes the first acquisition loop:

```text
Yandex Library
  -> Local Library
  -> Matching
  -> Missing
  -> one-click Download
  -> internal Wanted + persisted queue
  -> authorized provider download
  -> atomic final file
  -> normal Local Library index
  -> exact provider/local identity
  -> Coverage = covered
```

The backend invariant for an ordinary v0.7 enqueue is still:

```text
coverage_status = missing
user_action = wanted
```

For the user this is **not** a required two-step interaction. Pressing **Скачать** on a Missing row automatically persists `wanted`, enqueues the track and starts/joins the user queue. `Нужен` remains a triage/bulk-intent control.

`needs_review`, `conflict`, `not_analyzed`, `covered`, and `MATCHED + DIFFERENT_VERSION` are not automatic download candidates.

## Supported source

v0.7 supports the existing authenticated Yandex Music download workflow only. It does not implement YouTube ripping, VK scraping, torrents, pirate indexes, DRM circumvention, access bypass, web-search acquisition, or automatic fallback to another source.

The production download flow reads the Yandex token from `SystemCredentialStore` and passes it directly to `YandexMusicDownloadProvider`. Tokens and temporary direct URLs are not stored in SQLite, task payloads, filenames, or UI details. Historical provider fallback remains for old tools/reference acquisition only.

## Queue lifecycle

Persisted user states are:

```text
queued -> running -> completed
                  -> failed -> retry -> queued
                  -> cancelled
queued -> cancelled
queued -> skipped   (eligibility genuinely changed before execution)
```

`needs_review` is retained for review outcomes. `paused` is not offered because true pause/resume is not implemented.

The worker is intentionally sequential (`max concurrency = 1`). Reliability and deterministic SQLite state are preferred over parallel throughput in this release.

The user v0.7 bridge is scoped to `provider_download` tasks. Historical/reference-cache rows that share `download_tasks` are not shown in user counters/history and are not run, recovered, retried/cancelled or removed by v0.7 queue actions.

A stale persisted user `running` task can be recovered to `failed` with error code `interrupted`, after which Retry is available.

## Progress and cancellation

`YandexMusicDownloadProvider` streams response bytes directly to `<final>.part`.

When `Content-Length` is available the queue stores downloaded bytes, total bytes and percentage. Unknown total uses indeterminate progress. Progress persistence is throttled rather than writing every chunk.

Cancellation is cooperative. A running worker checks persisted `cancel_requested` between chunks. Cancellation removes `.part` and never promotes it to the final path. Retry starts from zero; v0.7 does not claim HTTP Range resume.

## Destination model

The Windows folder picker selects the **actual download folder**. MusicArk persists both:

- the Local Library root that owns the path;
- the exact selected normalized `target_path`.

Switching tabs or recreating `DownloadService` must return the same exact target. If the selected directory lies under an existing Local Library root, the parent root is retained for indexing while the exact selected subfolder remains the download destination. If it lies outside all roots, the selected folder becomes a Local Library root.

Every queued task snapshots `target_root_id` and exact `target_folder`, so changing the default later does not move existing work.

For databases that only have the older root setting and no `target_path`, the historical `<root>/MusicArk` target is used until the user selects a folder again.

Reference acquisition cache remains separate:

```text
.musicark/downloads/yandex/
```

It is not a user destination, is not inserted into Local Library, and is not shown as user Download history.

## Filename and write safety

Yandex downloads use a stable human-readable Windows-safe leaf name containing the provider ID, for example:

```text
Artist - Title [yandex_123456].mp3
```

Windows reserved characters/names, trailing dots/spaces and path traversal are sanitized/blocked. The provider verifies the final destination remains inside the task target folder.

Network writes are atomic:

```text
final.mp3.part -> final.mp3
```

A task is not completed merely because HTTP succeeded.

## Post-download integration

After the network transfer:

1. `LocalMetadataReader` must successfully parse the audio;
2. `LocalFileIndexer` reuses the v0.4 structured `LocalLibraryStorageRepository.apply_scan()` path with `allow_removals=False`;
3. the resulting `local_audio_files` row has a real `library_root_id` and `normalized_path`;
4. a `MatchDecision` is persisted with `MatchMethod.EXACT_ID`, confidence `1.0`, and reason `download_exact`;
5. the automatic matching fingerprint is computed after indexing;
6. Coverage is re-read and must be `covered` before the task becomes `completed`.

This fixes the legacy bug where a downloaded file could exist on disk but be invisible to v0.4 Local Library because `library_root_id` was `NULL`.

Exact acquisition identity does not run fuzzy candidate selection and does not fabricate `Variant = SAME`. Variant remains an independent layer.

The historical `wanted` action is retained after success. Since eligibility is `missing + wanted`, a covered track is no longer offered for ordinary download even though that decision remains in history.

## Schema 1.7.0

The forward migration extends the existing `download_tasks` table in place with downloaded/total bytes, cancellation state, target root, error code and update timestamp. It also creates generic `download_settings` and queue indexes.

Exact `target_path` persistence uses the existing key/value `download_settings` table and therefore needs no additional schema bump.

Existing queue rows, Yandex cache, Local Library, matching decisions, Variant results, and v0.6 wanted/ignored actions are preserved.

## UI

Navigation includes `Загрузки` after `Недостающие`.

Normal single-track use:

```text
Недостающие -> Скачать
```

No visit to the queue page and no prior `Нужен` click is required.

The Downloads page remains the progress/history/recovery surface and provides:

- queued/running/completed/error counters for user downloads only;
- All / queued / running / completed / error filters;
- exact persisted target-folder selection;
- `Скачать все «Нужные»` with automatic queue start;
- byte/percentage or indeterminate progress;
- Retry and Cancel;
- completed-history cleanup without deleting audio files;
- local file **Воспроизвести** and **Открыть расположение файла** actions;
- raw path hidden by default behind **Показать путь**.

Local Library rows expose the same play/reveal actions and hide the full path until explicitly expanded in track details.

v0.7 playback opens the local file in the OS default player. A real embedded MusicArk player (play/pause/seek/queue) is planned separately and is not falsely claimed by this release.

## Validation

Automated tests cover eligibility, duplicate identity/membership, exact target persistence across service recreation, exact post-download integration, non-NULL Local Library root, no fabricated Variant state, retry, recheck/skip, crash recovery, token-payload rejection, filename safety, v1.6 -> v1.7 migration, Content-Length progress, indeterminate progress, one-click Missing download UX, hidden-path/file actions, and `.part` cleanup on cancellation.

Manual Windows validation must begin with 1–3 tracks before any batch run. See `docs/testing/manual-test-plan.md`.
