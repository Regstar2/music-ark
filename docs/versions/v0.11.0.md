# MusicArk v0.11.0 — Production Single-Track Yandex Upload

## Status

v0.11.0 promotes the successful v0.10.0 direct-Python live proof into the production MusicArk architecture.

The protocol source of truth is the confirmed end-to-end result:

```text
Stage 1 HTTP 200
Stage 2 HTTP 201
playlist read-back verified=true
ambiguous=false
attemptsUsed=1
```

The production path does not import anything from `tools/`.

## Supported workflow

The Local Library exposes an explicit one-track action for a locally indexed MP3:

```text
Local Library
  -> Upload to Yandex Music
  -> choose one owned Yandex playlist
  -> confirm upload
  -> confirm upload rights
  -> production backend preflight
  -> Stage 1
  -> Stage 2
  -> bounded playlist read-back
```

The backend accepts `local_file_id`, not an arbitrary filesystem path from the UI. It resolves the indexed path itself and revalidates the file before any network mutation.

## Production protocol

Stage 1 is fixed to:

```text
POST https://api.music.yandex.net/loader/upload-url
```

with exactly:

```text
uid=<authenticated uid>
playlist-id=<uid>:<playlist kind>
path=<filename only>
```

No `visibility`, Authorization, OAuth, Cookie or browser credential is added by MusicArk.

The HTTPX client uses:

```text
http1=True
http2=True
trust_env=False
follow_redirects=False
```

with a bounded timeout and no automatic retry.

Stage 2 uses the dynamic `post-target` returned by Stage 1. Before sending audio bytes MusicArk requires a credential-free HTTPS URL hosted by a Yandex domain (`yandex.ru`, `yandex.net` or `yandex.com`, including their subdomains). Arbitrary hosts, HTTP, userinfo and redirects are rejected.

The multipart field name is exactly `file`. MusicArk does not copy Stage 1 headers or provider credentials into Stage 2. HTTP 201 is the expected successful transfer response.

## Read-back and uncertain delivery

Before upload MusicArk records the target playlist membership. After Stage 2 it performs bounded read-back using the Stage 1 `ugc-track-id` as the primary identity.

Result states include:

```text
verified
processing
delivery_unknown
stage1_failed
stage2_http_failed
preflight_failed
unsupported_format
ambiguous
```

A Stage 2 network/transport exception is deliberately not retried. The server may already have accepted the bytes, so an automatic retry could create a duplicate UGC track. MusicArk instead performs the same bounded playlist read-back:

- if the track is present, the result is `verified`;
- if the result is ambiguous, the result is `ambiguous`;
- if the file cannot be confirmed in the polling window, the result is `delivery_unknown` and the user is told to inspect the playlist before retrying manually.

A successful HTTP transfer that has not appeared by the end of the polling window is `processing`, not a failed upload.

## Preflight

Before Stage 1 MusicArk requires:

- an authenticated Yandex Music account with an authenticated UID;
- an existing target playlist owned by that account;
- an existing `local_file_id` in Local Library;
- a file that still exists and is non-empty;
- `.mp3` format;
- explicit upload confirmation;
- explicit rights confirmation.

No file-size limit is invented in v0.11.0.

## Security and privacy boundaries

Production upload results, audit events and Flutter payloads do not include:

- OAuth tokens;
- cookies;
- Authorization headers;
- authenticated UID;
- composite `uid:playlistKind` identifiers;
- signed `post-target` URLs;
- `poll-result` URLs;
- raw HTTP bodies or headers;
- arbitrary local filesystem paths as upload identity.

Signed upload URLs remain process-local and are never persisted. TLS verification is not disabled. CI uses only mocked/fake transport behavior and does not perform live Yandex mutations.

## Provider capability and Controlled Sync

`YandexMusicProvider` now truthfully reports:

```text
can_upload_tracks = true
supports_user_uploads = true
```

This capability means that an explicit manual production upload exists. It does not enable upload operations in `SyncPlanner` or Controlled Sync. v0.11.0 includes regression coverage for that boundary.

The old `experimental_yandex_upload` path remains a separate deprecated feasibility/research compatibility action. The old config/env flag is retained for backward compatibility but is not a production upload gate.

## Audit events

Manual upload writes only safe identifiers and typed state:

```text
upload_started
upload_verified
upload_processing
upload_failed
upload_delivery_unknown
```

Signed URLs, UID, credentials, raw HTTP responses and full Stage 1 queries are not stored.

## Limitations

v0.11.0 is intentionally narrow:

- MP3 only;
- one track at a time;
- manual Local Library action only;
- no bulk upload;
- no upload queue;
- no concurrent upload;
- no automatic retry;
- no automatic restoration;
- no SyncPlanner upload operation;
- no censorship replacement;
- no FLAC/OGG/M4A/WAV conversion or normalization;
- no production installer/release work in this milestone.

## v0.12.0 direction

The next upload milestone can build on this single-track safety boundary. Candidate work includes an explicit upload queue/batch workflow, controlled retries only where delivery is provably safe, richer processing refresh, and later integration with restoration/sync planning. Format conversion and censorship replacement remain separate concerns and should not be coupled to the first queue implementation.
