# MusicArk v0.10.0 — Yandex Upload Feasibility

## Final decision

**FEASIBLE at the Yandex Music service/protocol level.**

Yandex Music supports uploading user-owned local tracks for personal listening through the website and desktop application. Independent static analysis of the official desktop application also recovered a concrete UGC upload pipeline.

**NOT YET VERIFIED as a production MusicArk transport.**

MusicArk's current saved OAuth token plus the pinned Android-oriented `yandex-music==3.0.0` HTTP client has not yet been proven to reproduce the desktop upload request profile. Production upload capability therefore remains disabled.

This distinction is the final result of the v0.10.0 feasibility spike:

```text
Can Yandex Music accept a user-owned uploaded track?       YES
Does the official desktop client contain an upload flow?   YES
Is the transport structurally recoverable?                 YES
Has MusicArk verified one file end-to-end by read-back?     NO
Is production upload enabled?                              NO
```

## Product-level evidence

Current official Yandex Music documentation describes own-track upload for personal listening from the website or desktop application:

```text
select/create a user playlist
-> Upload track
-> select local files
-> playlist is stored by Yandex
-> uploaded collection is available on other devices
```

The supported product behavior is therefore not hypothetical. The remaining problem is reproducing the undocumented desktop/web transport safely inside MusicArk.

## Recovered desktop upload protocol

Static investigation of the official desktop `app.asar` used throughout the spike:

```text
SHA-256
8e7f4cec0776c39f194dee0a94086548d13f1465d46aa05d3e00a21624cbe80a
```

High-confidence findings from the official bundle:

1. Stage one uses the relative resource:

```text
POST loader/upload-url
```

2. `getUploadUrl(t, e)` reads/binds:

```text
uid          <- t.uid
playlist-id  <- t.playlistId
visibility   <- t.visibility
path         <- t.path
```

3. The upload model calls `getUploadUrl` with a structure containing:

```text
playlistId
uid
path
```

4. Stage two is a dynamic POST to the URL returned by stage one.

5. The body is multipart `FormData` with field:

```text
file
```

6. The dynamic upload path is intentionally separated from the ordinary Music API header set (`excludeHeaders` / `withoutHeaders`).

7. The desktop lifecycle contains:

```text
preparing
uploading
processing
retry / abort
checkProcessingTracks
moveTracksFromUploadCenterToPlaylist
```

This is enough to conclude that the service and official client use a real, reproducible two-stage UGC upload architecture rather than a purely local desktop feature.

## Live stage-one experiment

One explicit account-owned stage-one `prepare` request was attempted using MusicArk's existing authenticated Python client boundary.

The request used:

- an explicit user-owned local file;
- an explicit user playlist;
- stage one only;
- no audio-body transfer;
- no automatic fallback variants.

Result:

```text
RemoteDisconnected('Remote end closed connection without response')
```

Important interpretation:

- no HTTP status was received;
- no signed upload URL was returned;
- no stage-two request was sent;
- no audio bytes were uploaded;
- this does **not** prove that playlist UUID/path parameters were rejected;
- it does prove that blindly reusing the ordinary pinned Python request profile is not sufficient evidence for production use.

## Why the ordinary Python client is not considered proven

The pinned `yandex-music==3.0.0` client uses the normal Music API base URL and an Android-oriented client profile.

The official desktop bundle independently exposes desktop/web HTTP configuration concepts including:

```text
customApiPrefixUrl
customApiToken          (value never extracted)
getApiPrefixUrl
clientSafeConfig
clientRemoteType
createRequestHeaders
createSessionRequestHeaders
YandexMusicDesktopApp
YandexMusicWebNext
```

The spike deliberately did not extract or persist private token/cookie/session values and did not guess host/User-Agent/header combinations after the first inconclusive stage-one request.

## V9–V14 module investigation

The later probes tried to determine how the desktop UGC HTTP client is wired to its HTTP configuration without exposing raw JavaScript.

### V9

Established:

```text
module 39670
  -> upload/config model
  -> imports module 70204

module 70204
  -> contains UgcUploadHttpClient / BaseResourceHttpClient / ResourceHttpClient anchors
```

### V10

The importer uses exactly two stable provider export keys:

```text
r.Xc
r.RG
```

### V11

Both exports were confirmed in two independent layout chunks, but the direct definition parser could not map either export to the UGC client.

### V12

A broader safe identifier graph established a stable local owner for the UGC client in both independent chunks:

```text
UgcUploadHttpClient -> local owner u
```

No ordinary assignment/alias path connected `Xc` or `RG` to `u`.

### V13

A first destructuring probe was rejected by its own safety regression test because it could promote ordinary string contents into identifier output. The probe and its tests were removed rather than weakening the safety rule.

### V14

The replacement strict binding-form probe passed its safety tests and checked object destructuring, array destructuring and function-parameter bindings without emitting RHS string contents.

Result in both independent layout chunks:

```text
Xc/RG -> no object-destructure binding
Xc/RG -> no array-destructure binding
Xc/RG -> no parameter binding
```

Continuing to infer the concrete client role from minified `Xc/RG` names alone is therefore not a useful basis for a production implementation.

## Security boundary retained

The spike did not add:

- token CLI arguments;
- browser cookie extraction;
- persisted desktop/web session credentials;
- extraction of `customApiToken` values;
- CAPTCHA/MFA/security-challenge bypass;
- TLS verification bypass;
- live mutation in CI;
- automatic endpoint/header guessing;
- bulk upload;
- Upload UI;
- reverse Sync integration.

The obsolete experimental upload entry point remains fail-closed.

## What “possible” means after v0.10.0

The feasibility question is answered **YES** for the underlying feature and protocol.

It is **not** equivalent to saying that MusicArk can already upload reliably today. Before enabling the production provider capability, MusicArk still requires one guarded end-to-end proof:

```text
resolve the correct supported desktop/web stage-one request profile
-> obtain dynamic upload URL
-> upload one explicit user-owned file
-> wait for server processing
-> re-read the explicit target playlist
-> observe a new uploaded track identity
```

Only that read-back result may promote upload from experimental research to a production MusicArk capability.

## Recommended next implementation milestone

Do not continue broad minified-symbol archaeology as the primary strategy.

The next version should focus on the narrow remaining boundary:

1. determine a legitimate, reproducible desktop/web stage-one host and public client-header profile without extracting private embedded credentials;
2. reuse the existing MusicArk account credential only if the official request path demonstrably accepts it;
3. run exactly one explicit `prepare` experiment;
4. only after obtaining a signed upload URL, enable the already isolated stage-two one-file PoC;
5. require playlist read-back before reporting success;
6. keep provider capability flags disabled until that proof succeeds.

If the official desktop path turns out to require a private/custom credential unavailable through the user's normal MusicArk authentication boundary, the direct HTTP implementation should remain blocked rather than copying or extracting that credential.

## Non-goals

Not shipped in v0.10.0:

- production Upload UI;
- bulk upload/queue;
- reverse synchronization;
- automatic Matching/Coverage integration for uploaded tracks;
- format converter/transcoding;
- duplicate/idempotency policy;
- release build or installer changes.
