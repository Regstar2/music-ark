# MusicArk v0.5.0 — Matching

## Goal

Connect cached Yandex tracks with indexed Local Library files without downloading, modifying files, or calling external matching services.

```text
provider track identity
        ↓
limited local candidates
        ↓
transparent scoring
        ↓
matched / conflict / unmatched
```

The quality priority is automatic-match precision, not maximum recall.

## Reused legacy model

v0.5 keeps the existing canonical `tracks` table and confirmed `track_links`. `match_conflicts` is extended to hold multiple ranked candidates, score breakdown, matcher version, and durable rejection state. The legacy `MatchingEngine` remains as a compatibility facade but no longer contains the production algorithm.

No `canonical_tracks_v2` layer is introduced.

## Provider identity

The active Yandex cache stores membership in `provider_collection_items`. Before matching, `MatchingInputRepository` materializes unique provider identities into `provider_tracks` using `(provider_id, external_id)`. A track present in Liked and multiple playlists therefore receives one matching result.

## Local matching index

Migration `1.4.0` adds compact index columns to `local_audio_files`:

- `normalized_title`;
- `normalized_artists_text`;
- `duration_bucket`.

`LocalMatchIndex` refreshes these columns once per matching run so v0.4 scanning stays independent from matching internals. This is O(Local) once, not once per Yandex track.

SQL indexes support normalized title, artist+duration, duration bucket, match identity/status, and local-file link lookup.

## Normalization

`matching/normalize.py` is deterministic:

- Unicode NFKC;
- `casefold`;
- leading/trailing and repeated whitespace normalization;
- punctuation and dash variants treated as token boundaries;
- multiple artists normalized and compared order-independently;
- common `feat.` / `ft.` / comma / `&` forms split conservatively.

Meaningful version terms are never simply removed. `Live`, `Remix`, `Acoustic`, `Instrumental`, `Remaster`, `Demo`, `Radio Edit`, and related words remain part of the title signal.

## Candidate generation

`CandidateGenerator` asks SQLite for a bounded set instead of comparing every local file:

1. exact normalized title;
2. normalized title prefix variants;
3. exact normalized artist-set near duration buckets;
4. exact normalized artist-set fallback.

The detailed candidate limit is 40 per provider track. Candidate SQL returns compact structured metadata. Production matching contains no nested `for every Yandex × for every Local` loop.

## Scoring v1

Base weights:

```text
title    0.50
artists  0.30
duration 0.15
album    0.05
```

Missing optional signals are removed from the active denominator. Conservative caps prevent missing/wrong artist data, semantic-version mismatches, weak primary signals, or filename-only fallback from becoming unsafe auto-matches.

Duration policy:

```text
<= 1 s   1.00
<= 2 s   0.95
<= 5 s   0.80
<= 10 s  0.45
> 10 s   0.00
```

Duration is secondary and cannot create a match by itself. Album is supplementary. Filename is fallback below structured tags.

The historical `yandex_<track_id>.<ext>` convention remains a very strong exact-ID signal, but only under a strict filename pattern. An incidental number elsewhere in a path is not accepted.

## Decision policy

```text
AUTO_MATCH_THRESHOLD = 0.90
CONFLICT_THRESHOLD   = 0.70
AMBIGUITY_MARGIN     = 0.04
```

A candidate auto-matches only when its score is at least 0.90 and it beats the second candidate by at least 0.04. Otherwise a score at least 0.70 becomes `conflict`; weaker/no candidate becomes `unmatched`.

Two high-scoring files such as FLAC and MP3 versions of the same metadata therefore become a conflict instead of an arbitrary automatic choice.

## Persistence and incremental behavior

`matching_results` stores one result per provider identity with:

- state;
- chosen local file id;
- confidence;
- method;
- score breakdown;
- reason;
- `matcher_version`;
- provider fingerprint;
- local-library fingerprint;
- manual flag;
- timestamps.

Matching writes are batched in transactions. Unchanged automatic results can be skipped when matcher version and both fingerprints are unchanged.

If a linked local file disappears, its link is invalidated. Provider metadata changes alter its fingerprint and allow recomputation.

## Manual decisions

A manual accept:

- writes a confirmed `track_link` with `match_method=manual`;
- marks the matching result manual;
- survives normal automatic reruns.

A reject:

- records that exact candidate as `rejected` in `match_conflicts`;
- removes it from subsequent automatic candidate generation;
- lets remaining candidates continue to be reviewed.

Manual decisions have precedence over automatic decisions.

## Bridge / UI

Bridge commands:

```text
matching_summary
matching_run
matching_results
matching_result
matching_accept
matching_reject
```

Result listing supports `limit`, `offset`, `status`, `search`, and sort. The Flutter navigation adds **Сопоставление** with summary, run action, filters, search/sort, pagination, result rows, conflict details, and candidate accept/reject.

The process bridge continues to use `Process.run(..., runInShell: false)`. Matching accept/reject IDs are passed as structured argv values, not shell concatenation.

## Privacy / safety

Matching is local-only after Yandex cache and Local Library scan exist. It does not send local metadata to Yandex, OpenAI, external metadata services, or third-party match APIs.

v0.5 does not rename, move, delete, transcode, or edit local audio. It does not like/dislike tracks, edit playlists, upload, or otherwise mutate Yandex Music.

## Migration

Forward migration:

```text
1.3.0 (v0.4)
  ↓
1.4.0 (v0.5)
```

Existing Yandex collection snapshots/items, Local Library roots/files, canonical track links, and credentials remain in place. `initialize_database()` remains idempotent; users must not delete `.musicark/musicark.db` for the upgrade.

## Automated coverage

Python tests cover normalization, multiple artists/feat forms, semantic title variants, exact/weak scoring, duration/album behavior, strict exact-ID convention, ambiguity margin, automatic/conflict/unmatched persistence, manual decisions, rejection persistence, stale local files, duplicate collection membership, scale comparison bounds, and v0.4 → v0.5 migration preservation.

Flutter widget tests cover navigation, empty state, summary/run, filters, search, pagination, conflict detail, manual accept, and manual reject using fake bridges.

## Manual validation still required

Automated tests cannot establish precision on the user's real library. On Windows, validate Yandex Library + `C:\MusicArk-Test` or the existing test collection, including at least ten obvious matches, five difficult matches, live/remix/acoustic variants, and same-title/different-artist cases. False positives are the primary review target.

## Out of scope

v0.5 does not implement Missing Tracks workflow, download, sync, player/playback, metadata editor, rename/move/delete, Yandex upload, torrent integration, standalone packaging, or installer work.
