# MusicArk v0.7.0 — Download

## Product contract

v0.7 closes the first acquisition loop:

```text
Yandex Library
  -> Local Library
  -> Matching
  -> Missing
  -> Wanted
  -> Download queue
  -> authorized provider download
  -> atomic final file
  -> normal Local Library index
  -> exact provider/local identity
  -> Coverage = covered
```

An ordinary v0.7 enqueue is valid only when the derived coverage row is exactly:

```text
coverage_status = missing
user_action = wanted
```

`needs_review`, `conflict`, `not_analyzed`, `covered`, and `MATCHED + DIFFERENT_VERSION` are not automatic download candidates.

## Supported source

v0.7 supports the existing authenticated Yandex Music download workflow only. It does not implement YouTube ripping, VK scraping, torrents, pirate indexes, DRM circumvention, access bypass, web-search acquisition, or automatic fallback to another source.

The production download flow reads the Yandex token from `SystemCredentialStore` and passes it directly to `YandexMusicDownloadProvider`. Tokens and temporary direct URLs are not stored in SQLite, task payloads, filenames, or UI details. Historical provider fallback remains for old tools/reference acquisition only.

## Queue lifecycle

Persisted user-visible states are:

```text
queued -> running -> completed
                  -> failed -> retry -> queued
                  -> cancelled
queued -> cancelled
queued -> skipped   (eligibility changed before execution)
```

`needs_review` is retained for compatibility/review outcomes. `paused` is not offered in the v0.7 UI because true pause/resume is not implemented.

The worker is intentionally sequential (`max concurrency = 1`). Reliability and deterministic SQLite state are preferred over parallel throughput in this release.

A stale persisted `running` task can be recovered to `failed` with error code `interrupted`, after which Retry is available.

## Progress and cancellation

`YandexMusicDownloadProvider` streams response bytes directly to `<final>.part`.

When `Content-Length` is available the queue stores:

- downloaded bytes;
- total bytes;
- percentage.

When the size is unknown, the UI renders an indeterminate progress indicator. Progress persistence is throttled by time/byte thresholds rather than writing every 64 KiB chunk.

Cancellation is cooperative. A running worker checks the persisted `cancel_requested` flag between streaming chunks. Cancellation removes `.part` and never promotes it to the final path. Retry starts from zero; v0.7 does not claim HTTP Range resume.

## Destination model

The user selects a folder through the existing Windows folder picker. The selected folder becomes a Local Library root unless it already belongs to an existing root. The default managed destination is:

```text
<Local Library root>/MusicArk/
```

The selected root is persisted in `download_settings`; every queued task also snapshots `target_root_id` and `target_folder`, so changing the default later does not silently move existing queued work.

Reference acquisition cache remains separate:

```text
.musicark/downloads/yandex/
```

It is not a user download destination and is not inserted into Local Library.

## Filename and write safety

Yandex downloads use a stable human-readable Windows-safe leaf name containing the provider ID, for example:

```text
Artist - Title [yandex_123456].mp3
```

Windows reserved characters/names, trailing dots/spaces and path traversal are sanitized/blocked. The provider verifies the final destination remains inside the task target folder.

Network writes are atomic:

```text
final.mp3.part -> final.mp3
```

A task is not completed merely because HTTP succeeded.

## Post-download integration

After the network transfer:

1. `LocalMetadataReader` must successfully parse the audio;
2. `LocalFileIndexer` reuses the v0.4 structured `LocalLibraryStorageRepository.apply_scan()` path with `allow_removals=False`;
3. the resulting `local_audio_files` row has a real `library_root_id` and `normalized_path`;
4. a `MatchDecision` is persisted with `MatchMethod.EXACT_ID`, confidence `1.0`, and reason `download_exact`;
5. the automatic matching fingerprint is computed after the new local file is indexed;
6. Coverage is re-read and must be `covered` before the task becomes `completed`.

This fixes the legacy bug where a downloaded file could exist on disk but be invisible to v0.4 Local Library because `library_root_id` was `NULL`.

Exact acquisition identity does not run fuzzy candidate selection and does not fabricate `Variant = SAME`. Variant remains an independent layer.

The historical `wanted` action is retained after success. Since eligibility is `missing + wanted`, a covered track is no longer offered for ordinary download even though the historical decision remains visible in storage.

## Schema 1.7.0

The forward migration extends the existing `download_tasks` table in place with:

- `downloaded_bytes`;
- `total_bytes`;
- `cancel_requested`;
- `target_root_id`;
- `error_code`;
- `updated_at`.

It also creates `download_settings` and queue indexes. Existing queue rows, Yandex cache, Local Library, matching decisions, Variant results, and v0.6 wanted/ignored actions are preserved. `initialize_database()` applies v0.6 and then v0.7 sequentially, preventing a fresh/old database from skipping the v0.6 action table.

## UI

Navigation now includes `Загрузки` after `Недостающие`.

The Downloads page provides:

- queued/running/completed/error counters;
- All / queued / running / completed / error filters;
- persisted target folder selection;
- `Добавить все «Нужные»`;
- `Запустить очередь`;
- byte/percentage or indeterminate progress;
- Retry for failed/review tasks;
- Cancel for queued/running tasks;
- completed-history cleanup without deleting audio files.

A `missing + wanted` row on the Missing page also exposes `В загрузки` for single-track enqueue.

## Validation

Automated tests cover eligibility, duplicate identity/membership, exact post-download integration, non-NULL Local Library root, no fabricated Variant state, retry, recheck/skip, crash recovery, token-payload rejection, filename safety, v1.6 -> v1.7 migration, Content-Length progress, indeterminate progress, and `.part` cleanup on cancellation.

Manual Windows validation must begin with 1–3 tracks before any batch run. See `docs/testing/manual-test-plan.md`.
