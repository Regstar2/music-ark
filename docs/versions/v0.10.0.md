# MusicArk v0.10.0 — Yandex Single-Track Upload Feasibility

## Decision

**Yandex Music own-track upload is feasible and its two-stage desktop UGC protocol is recovered with high confidence.**

The second reverse-engineering round removed the earlier authorization blocker: the official stage-one request path structurally uses the normal account OAuth field and does not reference `customApiToken` on that path.

A production MusicArk upload capability is still **not enabled** because the last required end-to-end proof is runtime-specific: one real owned-file upload must produce a ground-truth stage-one host/profile and/or be verified through official-desktop-assisted playlist read-back.

Production capabilities remain:

```text
can_upload_tracks = false
supports_user_uploads = false
```

## Confirmed protocol

Official researched desktop `app.asar` SHA-256:

```text
8e7f4cec0776c39f194dee0a94086548d13f1465d46aa05d3e00a21624cbe80a
```

Recovered:

```text
stage 1
POST loader/upload-url
query: uid, playlist-id, visibility?, path

stage 2
POST <dynamic URL returned by stage 1>
multipart FormData field: file
ordinary Music API headers excluded

server lifecycle
preparing -> uploading -> processing
checkProcessingTracks
moveTracksFromUploadCenterToPlaylist
retry / abort
```

HTTP 2xx alone is never treated as success. Success requires one unambiguous newly observed playlist track identity.

## Previous live evidence

One guarded stage-one `prepare` was previously attempted through the ordinary pinned Android-oriented `yandex-music==3.0.0` request profile.

Observed:

```text
RemoteDisconnected('Remote end closed connection without response')
```

No HTTP status, dynamic URL, stage two, or audio transfer followed. This invalidates blind reuse of the ordinary Android request profile; it does not invalidate the upload protocol or account OAuth itself.

## Second-round authorization result

The relevant request modules are:

```text
stage-one resource: 12690
request stack:       31322
12690 -> 31322
```

Module `31322` structurally uses `prefixUrl`, `authorization`, and request headers.

The authorization lineage resolves to:

```text
common.oauth
this.config.params.common.oauth
Authorization scheme: OAuth
customApiTokenReferenced: false
```

Therefore the earlier hypothesis that a private packaged `customApiToken` is necessarily required for `loader/upload-url` is no longer the active blocker.

## Final static prefix result

The stage-one constructor uses a TLD-aware prefix expression:

```text
prefixUrl = getTldHost(arg0, arg1, TLD_MARK)
TLD_MARK = {tld}
```

V40 corrected a minified-local reuse error and proved that the actual first argument at the stage-one use site is:

```text
module 73202 property hooks
```

rather than the stale original module-32732 import binding of the reused local.

V41-V43 located module `73202` in:

```text
app/_next/static/chunks/2248.c548ad7dd602472d.js
```

but `hooks` is not exposed as a statically recoverable standard webpack named export, direct export, or CommonJS/object export in this packaged build. No allowlisted Yandex URL template can be proven from that runtime property without evaluating the running application.

**Static host/prefix investigation ends here.** Further source-form probes would not materially advance the proof.

## Direct HTTP implementation

`src/musicark/providers/yandex_upload_transport.py` includes `YandexOAuthStage1Requester`:

- requires an explicit HTTPS Yandex `base_url`;
- has no default or fallback host;
- posts exactly once to `<base_url>/loader/upload-url`;
- uses `Authorization: OAuth <saved MusicArk account token>`;
- sends no cookies;
- performs no automatic retry/host/header permutations;
- sanitizes failures.

`tools/yandex_upload_live_poc.py` accepts:

```text
--stage1-base-url <ground-truth-verified HTTPS Yandex prefix>
```

The OAuth token is resolved from the existing MusicArk credential boundary and is never accepted as a CLI argument.

Without `--stage1-base-url`, the direct PoC remains fail-closed before credential/network mutation.

## Official-desktop-assisted implementation

The branch now contains a complete runtime-ground-truth path:

- `tools/yandex_upload_runtime_trace.py` — immediate sanitization;
- `tools/yandex_upload_runtime_instrumentation.js` — optional secret-free renderer instrumentation;
- `tools/yandex_upload_cdp_probe.py` — localhost-only CDP collection;
- `tools/yandex_upload_ground_truth_analyzer.py` — extracts stage-one host/profile and stage2/processing structure;
- `tools/yandex_upload_desktop_assisted_poc.py` — playlist before/after verifier;
- `tools/yandex_upload_ground_truth_poc.py` — unified one-command orchestration.

The unified PoC:

1. launches or attaches to the visible official Yandex Music desktop app through localhost CDP;
2. snapshots the target playlist through MusicArk;
3. observes while the user performs exactly one normal owned-file upload in the official client;
4. sanitizes host/path/header-name/query-name/status/shape data immediately;
5. performs bounded MusicArk playlist read-back;
6. returns `verified` only for one unambiguous new track identity;
7. records a direct-HTTP decision if `/loader/upload-url` was observed.

This path never exports the official desktop credential.

## Success gate

A successful assisted proof is:

```json
{
  "transportMode": "official-desktop-assisted",
  "status": "verified",
  "readBack": {
    "verified": true,
    "ambiguous": false,
    "verifiedTrackId": "<new id>"
  }
}
```

If runtime observation also provides one unambiguous stage-one host/profile, the same evidence can be used for one controlled direct `prepare` through `YandexOAuthStage1Requester`.

## CI and safety

GitHub Actions remains strictly offline with respect to Yandex mutations.

The self-hosted research job validates:

- the exact official ASAR SHA;
- all upload-focused unit tests;
- authorization/query/stage2/read-back guards;
- runtime trace sanitization;
- CDP probe behavior through mocks;
- official-desktop-assisted state machine;
- direct OAuth stage-one construction;
- sanitized static research pipeline V15-V43;
- all declared no-secret/no-network safety flags.

The known broader Flutter widget baseline failures remain unrelated to upload. `flutter analyze --no-fatal-infos` is the relevant regression gate for this version's non-UI changes.

## Security boundary

The implementation does not persist or expose:

- account OAuth values;
- `customApiToken` values;
- Cookie/session values;
- Authorization values;
- signed upload URLs;
- raw HAR/CDP logs;
- browser profiles;
- copied `app.asar`;
- extracted frontend source.

No CAPTCHA/MFA bypass, TLS bypass, bulk upload, automatic stage-two retry, or live CI mutation is implemented.

## Remaining external proof step

All code required for the next proof is now in the branch. The only step that cannot be executed by GitHub Actions is intentionally interactive: perform exactly one visible owned-file upload in the authenticated official desktop client while running `tools/yandex_upload_ground_truth_poc.py` locally.

That single run can close either path:

```text
official desktop upload + MusicArk read-back -> verified

and, if stage one is observed:
ground-truth host/profile -> explicit OAuth direct prepare -> possible direct HTTP transport
```

Production upload flags remain false until that observed result exists.
