# MusicArk v0.6.0 — Missing Tracks / Library Coverage

## Goal

Answer two local questions without changing v0.5 matching semantics:

1. Which active Yandex tracks are proven absent from Local Library?
2. How much of the selected Yandex scope is covered, unresolved, or not yet analyzed?

## Authoritative semantics

| Matching/current state | Coverage |
|---|---|
| current accepted `MATCHED` / manual accepted link | `covered` |
| current `UNMATCHED` with no accepted current local link | `missing` |
| current `CONFLICT`, stale manual decision, invalid accepted link | `needs_review` |
| no result, stale automatic matcher/provider/local fingerprint | `not_analyzed` |

The forbidden shortcuts are `not matched → missing` and `reference cached → covered`.

Variant verification is independent. `MATCHED + SAME/ALTERED/DIFFERENT_VERSION/UNCERTAIN/NOT_CHECKED` is always identity `covered`; the variant state is reported separately.

## Architecture

```text
Flutter CoveragePage
        ↓
coverage_* process bridge
        ↓
LibraryCoverageService
        ↓
CoverageRepository (SQL)
        ↓
active provider_collection_items/snapshots
matching_results + track_links + match_conflicts
local_audio_files
track_variant_results
provider_track_actions
```

The service never runs its own matcher. `Run matching` delegates to the existing v0.5 Matching bridge/service.

## Scope and identity

Global identity is `(provider_id, external_id)`. A track in Liked and several playlists is counted once globally, while all memberships are returned for UI. Playlist duplicate storage keys are canonicalized from the payload provider ID. Playlist scope preserves the provider order.

Only active cached Yandex collection membership starts a coverage query, so removed provider tracks are not zombie Missing rows. Historical user actions may remain stored but cannot enter an active list unless the provider identity is active again.

## User triage

`provider_track_actions` stores only `wanted` or `ignored`. No row means `unreviewed`. Triage never changes matching or Yandex.

An old `wanted` action can remain historically after a rerun changes `missing → covered`; because future download selection starts from technical `missing`, that row no longer qualifies for v0.7.

## Reference audio

v0.5.1 explicit single-track verification may acquire a bounded exact reference into `.musicark/downloads/yandex`. It is verification-only. v0.6 never indexes it, never creates a `track_link` for it, and never treats it as Local Library coverage.

## Storage

Automatic forward migration `1.5.0 → 1.6.0` adds `provider_track_actions` and its action lookup index. No reset is permitted.

## Bridge

- `coverage_summary`
- `coverage_tracks`
- `coverage_track`
- `coverage_collections`
- `coverage_set_action`
- `coverage_set_actions`

Bulk IDs use a structured JSON environment payload rather than shell concatenation.

## UI

A fourth top-level section, **Недостающие**, opens on the `Missing` filter. It provides summary, scopes, search, sorting, primary filters, secondary variant filters, paginated `ListView`, row/details views, matching navigation, per-track triage, and bulk triage. No download control exists in v0.6.

## Validation gates

Central Python tests cover truth tables, variant independence, strict reference-cache regression, collection dedup/scopes/order, removed provider identities, actions across restart/rerun, stale automatic/manual state, bridge structured bulk payload, and the `1.5 → 1.6` migration. Flutter tests cover navigation, summary/default filter, scopes/search/sort/pagination, primary states, different-version warning, triage/bulk actions, details, matching navigation, and empty state.
