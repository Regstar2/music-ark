# Yandex Upload Runtime Ground-Truth Workflow

## Purpose

This workflow is the second-round v0.10.0 investigation after static analysis established the two-stage UGC protocol but could not prove the official desktop stage-one `prefixUrl + authorization` profile.

The goal is to observe one normal, visible, user-owned upload performed by the already-authenticated official Yandex Music desktop client while MusicArk records **only sanitized structure**.

The workflow has two independent outputs:

1. a local Chromium DevTools Protocol trace containing host/path, HTTP method, query/header names, status and structural response/runtime shapes;
2. a MusicArk playlist before/after verification showing whether one unambiguous new track identity appeared.

No raw HAR is created.

## New research tools

### `tools/yandex_upload_runtime_trace.py`

Shared sanitizer for CDP/runtime events.

Persisted network fields are limited to:

- scheme;
- hostname;
- path;
- query parameter names;
- header names;
- HTTP status;
- content-type classification;
- structural response shape.

It does not persist header/query values, cookies, authorization values, signed URL queries or raw response bodies.

### `tools/yandex_upload_runtime_instrumentation.js`

Optional renderer instrumentation injected through CDP.

It attempts to inspect/wrap the already-known webpack modules:

```text
12690
31322
```

It emits only:

- module/export/method identifiers;
- argument/result shapes;
- public `clientRemoteType` values;
- booleans indicating whether a `customApiPrefixUrl` or `customApiToken` path was present;
- credential-source classification when an exact known property can establish it.

It never reads browser cookie/local/session storage and never emits scalar credential/config values.

### `tools/yandex_upload_cdp_probe.py`

Local-only CDP collector.

It can attach to a Yandex Music Electron renderer opened with a local remote-debugging port and immediately sanitizes `Network.*` / runtime console telemetry before writing JSON.

The probe itself does **not** initiate an upload.

### `tools/yandex_upload_desktop_assisted_poc.py`

MusicArk verification side of the experiment.

It:

1. resolves the normal saved MusicArk account credential;
2. snapshots the explicitly selected user playlist;
3. waits while the user performs exactly one normal upload in the official desktop UI;
4. polls the same playlist through the normal Yandex provider boundary;
5. reports `verified` only for one unambiguous new track identity.

This is an `official-desktop-assisted` research transport, not production upload UI.

### `tools/yandex_upload_runtime_dataflow_probe.py`

Offline ASAR def-use probe.

It preserves only allowlisted upload/config property names and hashes all other local identifiers. Its purpose is to detect structural paths such as:

```text
customApiToken
-> alias:<hash>
-> authorization
```

or:

```text
customApiPrefixUrl
-> alias:<hash>
-> prefixUrl
```

without exposing minified identifiers, JavaScript source or values.

## Safety boundary

Do not commit or share:

- OAuth token values;
- `customApiToken` values;
- Cookie/session values;
- Authorization values;
- signed upload URLs;
- raw HAR;
- raw CDP logs;
- browser profiles;
- copied `app.asar`;
- extracted official JavaScript source.

Only the sanitized JSON generated by MusicArk research tools is suitable for review/artifacts.

## Local ground-truth experiment

Use a dedicated user-owned test playlist and exactly one user-owned local audio file.

### Terminal A — sanitized CDP trace

Close the existing desktop application first if it was not started with remote debugging.

From the MusicArk checkout:

```powershell
Set-Location C:\Base\projects\MusicArk

$YandexDir = Join-Path $env:LOCALAPPDATA "Programs\YandexMusic"
$YandexExe = Get-ChildItem -LiteralPath $YandexDir -Filter *.exe -File |
    Where-Object { $_.Name -notmatch 'Update|Uninstall|Squirrel' } |
    Sort-Object Length -Descending |
    Select-Object -First 1

if (-not $YandexExe) {
    throw "Could not locate the official Yandex Music executable."
}

.\.venv\Scripts\python.exe .\tools\yandex_upload_cdp_probe.py `
    --port 9222 `
    --duration 300 `
    --target-contains "Yandex" `
    --launch-exe $YandexExe.FullName `
    --output .\.musicark\research\yandex-upload-runtime-ground-truth.json
```

The official desktop UI remains visible. The collector does not trigger an upload.

### Terminal B — MusicArk before/after verification

Start this after the official desktop UI is open and before uploading the test file:

```powershell
Set-Location C:\Base\projects\MusicArk
$env:MUSICARK_EXPERIMENTAL_YANDEX_UPLOAD = "1"

.\.venv\Scripts\python.exe .\tools\yandex_upload_desktop_assisted_poc.py `
    --file "C:\PATH\TO\ONE_OWNED_TEST.mp3" `
    --playlist-kind 1055 `
    --confirm-owned-file `
    --confirm-desktop-upload `
    --readback-attempts 30 `
    --readback-delay 2
```

When prompted:

1. switch to the already-authenticated official Yandex Music desktop client;
2. open the exact target playlist;
3. use the normal **Upload track** UI;
4. select exactly the same one owned file;
5. wait until the official UI finishes its upload/processing indication;
6. return to Terminal B and press Enter.

Do not upload any other track into the target playlist during this observation window.

## Success definition

For the assisted path:

```json
{
  "transportMode": "official-desktop-assisted",
  "status": "verified",
  "readBack": {
    "verified": true,
    "ambiguous": false,
    "verifiedTrackId": "<new id>"
  }
}
```

For runtime ground truth, the sanitized CDP report should ideally contain:

- a request with path `/loader/upload-url`;
- its actual hostname;
- exact query parameter names;
- exact header names;
- whether `authorization` is present;
- a response status and structural response shape;
- a later multipart POST candidate for stage two;
- processing/UGC requests if visible;
- runtime events from modules `12690` / `31322` if the current renderer exposes those modules to instrumentation.

The signed upload URL value is intentionally never recorded.

## Interpretation

### OBSERVED

Only facts present in the sanitized runtime report or playlist read-back may be called observed.

### INFERRED

Credential source may be inferred only when runtime instrumentation or hashed def-use evidence links a known property (`customApiToken`, account OAuth property, session property) to request construction. Presence of the property name elsewhere is insufficient.

### NOT PROVEN

A working official-desktop-assisted upload does not by itself prove that MusicArk can reproduce the same request through direct HTTP. Direct transport remains a separate gate.

## Production state

This workflow does not change provider capabilities:

```text
can_upload_tracks = false
supports_user_uploads = false
```

No live upload is run in GitHub Actions.
