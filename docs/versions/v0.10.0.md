# MusicArk v0.10.0 — Yandex Single-Track Upload Feasibility

## Final decision

**Yandex Music own-track upload is feasible at the service/protocol level.**

**Direct MusicArk single-track upload through the existing OAuth credential boundary is BLOCKED.**

The official product accepts user-owned local tracks, and the official desktop application contains a concrete two-stage UGC upload flow. MusicArk recovered that flow far enough to implement and test the protocol shape, but it cannot legitimately reproduce the production stage-one `prefixUrl + authorization` profile without using opaque/private desktop runtime configuration.

Production capabilities remain disabled:

```text
can_upload_tracks = false
supports_user_uploads = false
```

## Confirmed upload protocol

Official researched desktop `app.asar` SHA-256:

```text
8e7f4cec0776c39f194dee0a94086548d13f1465d46aa05d3e00a21624cbe80a
```

Recovered with high confidence:

```text
stage 1
POST loader/upload-url
query: uid, playlist-id, visibility?, path

stage 2
POST <dynamic URL returned by stage 1>
multipart FormData field: file
ordinary Music API headers excluded

server lifecycle
preparing -> uploading -> processing
checkProcessingTracks
moveTracksFromUploadCenterToPlaylist
retry / abort
```

HTTP 2xx alone is not success. A future successful implementation must re-read the target playlist and observe one unambiguous new track identity.

## Live stage-one evidence

One explicit account-owned `prepare` was previously attempted through the ordinary pinned `yandex-music==3.0.0` client profile.

Observed:

```text
RemoteDisconnected('Remote end closed connection without response')
```

No HTTP status was returned, no dynamic URL was obtained, stage two was not sent, and no audio bytes were uploaded.

The pinned Python client is Android-oriented. The failure therefore does not establish a bad UUID/path; it establishes that the ordinary provider client is not a verified reproduction of the desktop UGC request.

## Final runtime-profile investigation

The late-stage investigation stopped broad minified-symbol archaeology and focused only on the runtime request profile used by `loader/upload-url`.

### Stage-one module wiring

The official upload chunk resolves:

```text
module 12690
  anchors: loader/upload-url, getUploadUrl, createHttpOptions
```

The stage-one module directly imports request-construction module:

```text
12690 -> 31322
```

Module `31322` exposes the structural request machinery:

```text
createHttpOptions
createRequestHeaders
prefixUrl
authorization
headers
```

This confirms that the official upload resource depends on a configured prefix/authorization layer rather than merely appending `loader/upload-url` to any arbitrary Music API client.

### Production runtime configuration

Sanitized scanning of the packaged production runtime observes:

```text
customApiPrefixUrl:
  non-empty opaque string in 79 members

customApiToken:
  non-empty redacted sensitive value in 81 members

prefixUrl:
  empty-string forms in 2 members
  identifier/reference forms in 10 members
```

The custom prefix remains opaque after safe JSON unescape. It is not recoverable as an allowlisted public Yandex HTTP(S) host/path or safe relative prefix without exposing arbitrary runtime string values.

The custom token value was never emitted, inspected, copied, requested, or committed.

## Exact blocker

MusicArk knows the stage-one request **shape**, but has no verified public production contract for the required `prefixUrl + authorization` profile.

The official desktop package uses opaque custom API runtime configuration. The project rules prohibit extracting/copying the packaged private token, arbitrary opaque prefix values, browser cookies, session credentials, or guessing hosts/header combinations.

Therefore the exact blocker is:

> **No verified public stage-one prefix/authorization contract is available through MusicArk's existing OAuth credential boundary, while the official desktop production request is wired to opaque custom API configuration.**

This is a transport/authentication blocker, not evidence that Yandex's own upload feature is unavailable.

## Implementation state

`src/musicark/providers/yandex_upload_transport.py` now fails closed for stage one:

- no default `client.base_url` fallback;
- no silent reuse of the Android-oriented `yandex-music` request profile;
- `prepare_upload()` requires an explicitly injected, independently verified stage-one requester;
- without such a requester, it raises a BLOCKED error before an upload request is sent;
- the recovered `uid / playlist-id / visibility / path` mapping remains unit-testable offline;
- stage-two multipart `file` upload remains isolated and testable without Yandex OAuth/session headers.

`tools/yandex_upload_live_poc.py` also fails closed before credential resolution, playlist reads, or upload mutation. Even setting the live environment flag cannot bypass the missing verified stage-one profile.

## Read-back correctness

The PoC now prevents a false success when the playlist changes concurrently:

- reported stage-two ID verifies only if it is a newly observed ID;
- exactly one new ID may verify through before/after set difference;
- multiple unknown new IDs are marked ambiguous and remain `uploaded_unverified`;
- success still requires `readBack.verified == true`.

## Security boundary

Not implemented and not permitted as a workaround:

- extraction/copying of `customApiToken`;
- arbitrary opaque runtime-prefix extraction;
- browser cookie/session extraction;
- CAPTCHA/MFA/security challenge bypass;
- TLS verification bypass;
- guessed host/User-Agent/header brute force;
- second hidden login flow;
- live upload in CI.

## Not shipped in v0.10.0

- production Upload UI;
- bulk upload/queue;
- reverse Sync;
- automatic Matching/Coverage integration;
- format converter/transcoding;
- duplicate policy;
- background uploader;
- packaging/release changes.

## Reopening direct upload

The direct HTTP path can be reopened only when a legitimate source provides the missing stage-one profile, for example:

1. Yandex publishes/supports a user-file upload API using normal account credentials;
2. an approved client library exposes a documented upload API;
3. a future official client exposes a public, non-secret prefix/client profile that can be structurally tied to `loader/upload-url` without extracting private credentials.

Until then, MusicArk must not retry live `prepare` using the old ordinary OAuth/Android profile.
