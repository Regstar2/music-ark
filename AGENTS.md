# AGENTS.md

## Проект

Этот репозиторий содержит **MusicArk**.

**MusicArk** — кроссплатформенное приложение для сохранения, анализа, восстановления и синхронизации личной музыкальной коллекции между локальным архивом и внешними музыкальными провайдерами.

Первый практический провайдер — **Яндекс Музыка**, но архитектура приложения должна оставаться универсальной и не должна быть жёстко привязана к Яндекс Музыке.

Яндекс Музыка — первая реализация, а не центр архитектуры.

## Целевая платформа первого этапа

Первый этап разработки MusicArk ориентирован на ПК / desktop.

Desktop-first выбран потому что на ПК проще:

- работать с локальным музыкальным архивом;
- индексировать большие папки с аудиофайлами;
- тестировать provider-интеграции;
- отлаживать matching-логику;
- управлять локальной базой данных;
- реализовывать восстановление коллекции;
- экспериментировать с download system;
- запускать и отлаживать integration-тесты.

Android-версия является будущей целью, но не должна влиять на архитектуру ранних версий.

`core` должен оставаться платформенно-независимым, чтобы позже его можно было использовать и в desktop-приложении, и в Android-приложении.

## Процесс разработки

Работай по одной версии за раз.

Не реализуй будущие версии раньше времени.

Для каждой версии:

1. Прочитай этот `AGENTS.md`.
2. Прочитай `docs/project-map/index.md`.
3. Прочитай нужный файл версии.
4. Прочитай соответствующий Codex-промт.
5. Изучи текущую структуру репозитория.
6. Перед изменениями кратко сформулируй план реализации.
7. Реализуй только область текущей версии.
8. Добавь или обнови тесты там, где это разумно.
9. Обнови документацию, если изменилось поведение, структура или архитектурные правила.
10. В конце опиши созданные файлы, изменённые файлы, тесты, документацию и оставшуюся работу.

## Definition of Done для каждой версии

Каждый этап разработки считается завершённым только если вместе с кодом обновлены документация и тесты.

Для каждой версии обязательно выполнить три части:

1. Реализация функциональности текущей версии.
2. Документация по правилам проекта.
3. Тесты для новой или изменённой логики.

Нельзя считать версию завершённой, если код написан, но документация или тесты проигнорированы без явного объяснения.

Если документация или тесты не были добавлены, в итоговом отчёте нужно явно объяснить причину.

Формулировки без объяснения вроде:

- `тесты не добавлены`;
- `документация не обновлялась`;
- `проверки не запускались`;

не допускаются.

Нужно писать конкретно:

- почему тесты не добавлены;
- почему документация не изменилась;
- почему проверки не запускались;
- какие риски из-за этого остаются.

Для каждой версии нужно добавлять или обновлять тесты там, где появляется новая логика.

Особенно важно тестировать:

- provider capabilities;
- переходы состояния download task;

- matching-логику;
- работу с локальными файлами;
- работу с метаданными;
- операции базы данных;

Обычные unit-тесты должны быть быстрыми и не должны требовать:

- сети;

- токена Яндекс Музыки;

- локальных файлов пользователя;
- конкретной ОС;
- ручных действий пользователя.

Для внешних provider’ов использовать:

- fixtures;
- mocks;
- fake implementations;
- заранее сохранённые обезличенные примеры ответов API.

Integration-тесты с реальными сервисами добавлять только в версиях, где это уместно, и делать их необязательными для обычного запуска.

Если для версии нет разумных тестов, в итоговом отчёте нужно явно объяснить почему.

Формулировка “тесты не добавлены” без причины не допускается.

Плохие тесты ради галочки не нужны.

Плохо:

```python
def test_true():
    assert True
```

Такой тест не проверяет систему, а просто изображает уверенность. Это бесполезно.

Хорошо:

```python
def test_provider_track_id_is_not_used_as_global_track_id():
    ...
```

Тест должен защищать важное поведение, архитектурное правило или обработку ошибки.

## Integration-тесты Яндекс Музыки

Integration-тесты Яндекс Музыки добавляются только на версии, где реализуется соответствующий provider.

Обычные unit-тесты не должны требовать:

- реального аккаунта;
- токена Яндекс Музыки;
- сети;
- конкретного состояния пользовательской коллекции.

Для локальных integration-тестов можно использовать значения из `.env`, `local.properties` или другого локального файла конфигурации, который не попадает в Git.

Пример локальных значений:

```properties
YANDEX_MUSIC_TOKEN=
YANDEX_MUSIC_EXPECTED_MIN_TRACKS=100
YANDEX_MUSIC_EXPECTED_FIRST_TRACK_ID=
YANDEX_MUSIC_EXPECTED_FIRST_TRACK_TITLE=Courtesy Call
YANDEX_MUSIC_EXPECTED_FIRST_TRACK_ARTIST=Thousand Foot Krutch
```

Если `YANDEX_MUSIC_TOKEN` не задан, integration-тесты должны пропускаться, а не падать.

Если `YANDEX_MUSIC_EXPECTED_FIRST_TRACK_ID` не задан, тест может вывести фактический ID первого трека в безопасный лог, не раскрывая токен.

Токен запрещено:

- коммитить;
- логировать;
- добавлять в fixtures;
- вставлять в документацию;
- передавать в Codex-промты;
- сохранять в raw-виде без необходимости.

Integration-тесты Яндекс Музыки могут проверять:

- успешную авторизацию;
- загрузку коллекции;
- минимальное количество треков;
- первый трек коллекции:
  - `Courtesy Call`
  - `Thousand Foot Krutch`;
- ID первого трека, когда он будет известен;
- корректный маппинг provider-specific данных в универсальные модели MusicArk.

## Архитектурные правила

### Core

Модуль `core` должен оставаться независимым от:

- UI;
- платформенного кода;
- конкретных API музыкальных сервисов;
- Android-деталей;
- Windows-деталей;
- прямых объектов библиотеки Яндекс Музыки;
- конкретной реализации скачивания.

`core` должен работать с универсальными моделями MusicArk.

`core` не должен импортировать provider-specific DTO, API clients или platform-specific storage APIs.

### Providers

Музыкальные сервисы должны подключаться через provider-адаптеры.

Не зашивай архитектуру приложения вокруг Яндекс Музыки.

Правильные понятия:

- `providers`
- `provider-capabilities`
- `track-source`
- `yandex-music-provider`
- `future-providers`

Неправильно:

- класть Яндекс-специфичную логику в `core`;
- делать ID трека Яндекс Музыки главным идентификатором всей системы;
- писать `if provider == "yandex"` по всему коду;
- вызывать API Яндекс Музыки напрямую из UI;
- строить sync-логику вокруг возможностей одного провайдера.

Каждый provider должен объявлять свои capabilities.

Не предполагай, что каждый provider поддерживает:

- скачивание;
- загрузку файлов;
- редактирование плейлистов;
- лайкнутые треки;
- пользовательские загрузки;
- статус доступности трека;
- точные даты добавления;
- одинаковую модель альбомов и исполнителей.

### Download system

Музыкальные провайдеры и download provider’ы — разные сущности.

Музыкальный provider описывает музыкальный сервис или источник коллекции.

Download provider описывает механизм получения файлов.

Скачивание должно идти через `download-system`.

Правильный поток:

```text
sync-planner
-> download-task
-> download-system
-> download-provider
-> local-audio-file
-> matching-engine
-> canonical-library
```

Не вызывай методы скачивания Яндекс Музыки напрямую из UI или sync-логики.

Download system должен уметь работать с разными download provider’ами, включая будущие backend’ы.

### Sync

Планирование синхронизации и выполнение синхронизации должны быть разделены.

`sync-planner` только анализирует состояние и строит план.

`sync-executor` выполняет подтверждённые операции.

Опасные операции должны требовать явного подтверждения пользователя:

- удаление;
- замена;
- загрузка файлов в сервис;
- массовое изменение метаданных;
- изменение плейлистов;
- массовое скачивание, если оно может вызвать ограничения сервиса.

`sync-planner` не должен изменять состояние коллекции.

`sync-planner` должен возвращать план, который можно показать пользователю до выполнения.

### Local archive

Локальный архив — главный слой сохранности коллекции.

Локальный файл представлен сущностью `local-audio-file`.

Музыкальная сущность представлена сущностью `track`.

Источник трека представлен сущностью `track-source`.

Не считай путь к файлу единственным идентификатором трека.

Предпочитай стабильные идентификаторы и данные:

- sha256;
- длительность;
- кодек;
- битрейт;
- нормализованное название;
- нормализованных исполнителей;
- источник провайдера;
- аудио-отпечаток в будущих версиях, если будет реализован.

Локальный файл может существовать без связи с provider track.

Provider track может существовать без локального файла.

Связь между ними должна строиться через matching-логику, а не через случайное совпадение строки пути.

### Metadata

Работа с метаданными должна быть явной и безопасной.

Не переписывай теги молча.

Массовое изменение метаданных должно требовать подтверждения.

Любое изменение метаданных должно записываться в audit log.

Metadata engine не должен автоматически считать provider metadata более правильными, чем локальные теги.

Пользователь должен понимать, какие поля будут изменены до применения операции.

### Audit log

Любая операция, изменяющая состояние приложения, должна логироваться.

Audit log должен объяснять:

- что произошло;
- когда это произошло;
- какой трек, файл или источник был затронут;
- успешно ли завершилась операция;
- какая ошибка возникла, если операция не удалась.

Особенно важно логировать:

- скачивание;
- удаление;
- изменение метаданных;
- sync-операции;
- восстановление;
- загрузку файлов в provider;
- массовые операции;
- ошибки provider API.

### Torrent support

Поддержка BitTorrent — будущая функция.

Не реализуй torrent support раньше запланированной будущей версии.

Архитектура должна позволять добавить torrent позже как download provider.

Torrent не должен быть частью Yandex Music provider.

MusicArk не должен содержать публичную базу torrent/magnet-ссылок на коммерческие треки.

Когда torrent support будет реализован, он должен принимать только пользовательские `.torrent` файлы или magnet-ссылки.

BitTorrent должен использоваться только как механизм загрузки пользовательских или легально доступных файлов.

### Future providers

Будущие музыкальные сервисы должны добавляться как provider-адаптеры.

Не реализуй future providers раньше запланированной будущей версии.

Каждый provider должен объявлять свои capabilities.

Не предполагай, что каждый сервис поддерживает:

- скачивание;
- загрузку файлов;
- редактирование плейлистов;
- лайкнутые треки;
- пользовательские загрузки;
- статус доступности трека.

## Безопасность и приватность

Никогда не хардкодь пользовательские токены.

Никогда не коммить токены, cookies, приватные headers или данные аккаунта.

Токены должны загружаться из конфигурации, переменных окружения или безопасного хранилища в зависимости от платформы.

Не выводи токены в логи.

Не сохраняй чувствительные auth-данные в raw-виде, если это не требуется явно и не защищено.

Не добавляй реальные пользовательские данные в fixtures.

Не добавляй приватные данные аккаунта в документацию.

Для примеров используй явно фейковые значения.

Плохо:

```text
Authorization: OAuth real_token_here
```

Хорошо:

```text
Authorization: OAuth <YANDEX_MUSIC_TOKEN>
```

Если нужно логировать token-related ошибку, логируй только факт ошибки, а не сам токен.

## Обработка ошибок

Обрабатывай ожидаемые ошибки явно:

- отсутствующий токен;
- невалидный токен;
- ошибка сети;
- изменение API провайдера;
- недоступный трек;
- ошибка скачивания;
- ошибка чтения или записи метаданных;
- ошибка базы данных;
- неподдерживаемая capability провайдера;
- отменённая операция;
- конфликт локальных и provider-данных;
- повреждённый локальный файл;
- недостаток прав доступа к файлам;
- недоступная директория библиотеки.

Не прячь полезные детали за бесполезным сообщением “что-то пошло не так”.

Ошибка должна быть достаточно понятной для пользователя или разработчика.

Пользователю не нужно показывать stack trace.

Разработчику нужно оставить достаточно информации в логах, не раскрывая секреты.

## Тестирование

Добавляй тесты для модулей с важной логикой.

Особенно полезны тесты для:

- сериализации моделей;
- маппинга данных провайдера;
- переходов состояния download task;
- matching-логики;
- sync planning;
- изменения метаданных;
- операций базы данных;
- обработки ошибок;
- audit log;
- provider capabilities;
- проверки запрета опасных операций без подтверждения.

Обычные автоматические тесты не должны требовать реальных данных аккаунта Яндекс Музыки.

Используй fixtures или mocks для ответов провайдеров.

Для новых модулей желательно иметь хотя бы минимальные тесты, которые защищают:

- основное успешное поведение;
- одну-две важные ошибки;
- архитектурные ограничения, если их можно проверить автоматически.

## Стиль документации

Документация должна быть в Markdown.

Используй существующие файлы в `docs/`.

Когда добавляется новый модуль или меняется важная концепция, обновляй соответствующую документацию.

При ссылках на проектные понятия в документации используй Obsidian-style ссылки:

```text
[[core]]
[[download-system]]
[[yandex-music-provider]]
[[sync-planner]]
```

Название ссылки должно совпадать с именем markdown-файла без расширения.

Документация должна быть конкретной.

Плохо:

```text
Модуль делает разные полезные вещи для музыки.
```

Хорошо:

```text
Модуль `matching-engine` сопоставляет локальные аудиофайлы с provider track через нормализованные названия, исполнителей, длительность и будущие audio fingerprint признаки.
```

## Стиль кода

Предпочитай простой и читаемый код.

Избегай переусложнения.

Избегай огромных manager-классов.

Не смешивай разные ответственности в одном модуле.

Предпочитай небольшие модули с понятными границами.

Не создавай абстракции ради будущих функций, если текущая архитектура ещё не требует такой точки расширения.

Но если архитектурное правило уже явно задано в roadmap, не ломай его ради краткосрочного удобства.

Плохо:

```text
YandexMusicMegaManager
```

Хорошо:

```text
YandexMusicClient
YandexMusicMapper
YandexMusicProvider
ProviderCapabilities
```

## Комментарии и документация в коде

Пиши комментарии и документационные комментарии сразу во время реализации.

В зависимости от языка используй подходящий формат:

- docstring;
- JavaDoc;
- KDoc;
- TSDoc;
- XML documentation comments;
- другой стандартный формат выбранного языка.

Комментарии должны объяснять:

- назначение модуля;
- ответственность класса или функции;
- неочевидные архитектурные решения;
- причины ограничений;
- важные side effects;
- связь с модулями из документации;
- почему операция безопасна или требует подтверждения;
- почему функция является заглушкой для будущей версии.

Комментарии не должны пересказывать очевидный код.

Плохо:

```python
# increment counter
counter += 1
```

Хорошо:

```python
# Track source IDs are provider-specific, so they must not be used
# as global MusicArk track identities.
```

Для публичных классов, сервисов и важных функций добавляй документационные комментарии.

Документационный комментарий должен кратко отвечать:

- что делает объект;
- за что он отвечает;
- с какими модулями связан;
- чего он специально не делает.

Для временных заглушек используй явные TODO с указанием версии:

```python
# TODO(v0.6-yandex-download): implement real Yandex Music download provider.
```

Не оставляй безымянные TODO вроде:

```python
# TODO fix later
```

Это не TODO, а записка будущему страдальцу.

Особенно важно документировать:

- [[core]];
- [[providers]];
- [[download-system]];
- [[download-task]];
- [[download-provider]];
- [[sync-planner]];
- [[sync-executor]];
- [[matching-engine]];
- [[metadata-engine]];
- [[storage]];
- [[platform-bridge]].

Если код реализует архитектурное правило из документации, добавь короткий комментарий рядом с местом, где это правило важно.

## Дисциплина версий

Текущая реализация должна соответствовать только запрошенной версии.

Если промт просит реализовать `v0.1-core-foundation`, не реализуй:

- Яндекс Музыку;
- UI;
- download system;
- matching;
- sync planner;
- metadata editor;
- Android;
- torrent;
- future providers.

Если для будущей функции нужен placeholder, создай маленькую явную заглушку или TODO со ссылкой на запланированную версию.

Нельзя использовать текущую версию как повод заранее реализовать половину roadmap.

Это создаёт хаос, а потом все делают вид, что “так исторически сложилось”.

## Главное напоминание

MusicArk архитектурно не зависит от конкретного сервиса, но первая реализация ориентирована на Яндекс Музыку.

Не превращай проект в одноразовый Yandex backup script.

Каждая версия должна оставлять после себя не только код, но и понятную документацию с тестами.

Иначе это не разработка, а раскладывание мин для будущего себя.
