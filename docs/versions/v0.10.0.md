# MusicArk v0.10.0 — Yandex Upload Feasibility Spike

## Goal

Determine whether MusicArk can reproducibly and safely upload one explicitly selected, user-owned local audio file into the authenticated user's Yandex Music collection using the existing MusicArk credential boundary.

This milestone is research-first. It does not ship a user-facing upload feature.

## Baseline

- baseline branch: `main`
- baseline commit: `c67489417930dd61bab150c1cd1b3bf57cc1abd0`
- source/application version before this milestone: `0.9.7` in `pyproject.toml` / Flutter, while `src/musicark/__init__.py` had drifted to `0.9.5`
- SQLite schema: `1.8.4`
- Yandex dependency pin: `yandex-music==3.0.0`
- production provider capabilities before and after the spike: `can_upload_tracks = false`, `supports_user_uploads = false`

The v0.9.x UI line is treated as complete. v0.10.0 is the first upload-feasibility milestone.

## Research method

The investigation followed the required order:

1. inspect the repository dependency pin and current Yandex provider boundary;
2. inspect the source/API surface of the pinned `yandex-music` release;
3. inspect current primary Yandex Music user documentation for own-track upload behavior;
4. compare those facts with the pre-existing MusicArk experimental upload scaffold;
5. reject any implementation that would require guessed endpoints, guessed multipart fields, browser-cookie extraction, CAPTCHA/MFA bypass, TLS weakening or a second login flow.

No real Yandex upload request was sent during this implementation because no reproducible authenticated protocol was established.

## Observed upload workflow

Official Yandex Music documentation confirms a user-facing own-track workflow:

```text
website or desktop application
  -> create/select a user playlist
  -> Upload track
  -> choose local files
  -> resulting playlist is stored by Yandex and is available on other devices
```

The same documentation says own tracks cannot be uploaded directly into `Мне нравится`, another user's playlist or an editorial playlist.

It also documents that artwork, track title and artist are read from the uploaded file, with title/artist editable afterward.

These are product/UI semantics, not a published HTTP upload contract.

## Protocol findings

No primary source inspected for this spike documents the HTTP endpoint, method, multipart/body fields, request content type, upload-session lifecycle or response schema for user-file upload.

The pinned `yandex-music==3.0.0` client does not provide a verified public method that MusicArk can call to perform this user-file upload flow.

Therefore v0.10.0 does not guess or reverse-engineer a request from memory, stale snippets or method-name heuristics.

## Authentication findings

MusicArk already has an authenticated Yandex provider boundary and secure credential storage. That is sufficient for current supported provider reads/download flows.

For own-track upload, however, the investigation did not establish whether the existing token alone is accepted, whether additional cookies/CSRF/session artifacts are required, or whether desktop/web clients perform an additional challenge. These values remain unknown.

No browser cookie extraction, second Yandex login, Selenium/Playwright automation, CAPTCHA/MFA handling or security-challenge emulation was added.

## Target collection semantics

Confirmed from Yandex Music Help:

- upload targets a user-created/user-owned playlist;
- upload is not available directly to `Мне нравится`;
- upload is not available to another user's or an editorial playlist;
- the resulting playlist is synchronized through the Yandex account.

Whether the undocumented transport accepts an explicit playlist ID, creates an upload collection implicitly, or performs multiple requests is `NOT DOCUMENTED`.

## Response semantics

No verified server response contract was found.

The following remain unknown:

- stable uploaded track identity;
- returned track ID;
- returned playlist/collection ID;
- duplicate response semantics;
- retry/idempotency token;
- post-upload processing state.

Because a stable identity is not confirmed, v0.10.0 does not create Matching/Coverage links or claim trusted identity after upload.

## Security constraints

The feasibility result deliberately keeps the existing secure boundary intact:

- no token CLI argument;
- no token/cookie fixture;
- no browser-cookie extraction;
- no persisted upload credential/session table;
- no signed/temporary URL fixture;
- no TLS-validation bypass;
- no CAPTCHA/MFA/security-challenge bypass;
- no real mutation in CI;
- no Upload UI, queue or Sync operation.

The pre-existing experimental upload scaffold previously read a Local Library file and could write the resolved local path plus probe payload into the audit log even though no upload protocol existed. v0.10.0 changes that compatibility path to fail closed before file/database/provider access and before any Yandex request.

## Proof-of-concept

No upload proof-of-concept is included.

Creating one without a verified request/authentication/response contract would be a guessed implementation and would not satisfy the SUCCESS definition.

The old developer command remains only as a fail-closed compatibility entry point: invoking it raises a BLOCKED error and explicitly states that no upload request was sent. It is not a live probe and is not a production capability.

Repository-level regression coverage added for:

- `YandexMusicProvider.supports_user_uploads == false`;
- compatibility probe reports no verified API;
- obsolete experimental entry point fails closed.

GitHub Actions is the authoritative executable gate for this connector-authored branch. Local Python/Flutter/Windows execution is recorded only if actually run; no live upload test is eligible while the milestone is BLOCKED.

## Outcome

BLOCKED

The user-facing Yandex Music upload feature exists, but this spike did not establish a reproducible, safe programmatic protocol that can be authenticated through MusicArk's existing credential boundary. Endpoint/method/body/authentication/response identity remain unverified. Implementing production Single Track Upload now would require guessing undocumented behavior or introducing a browser/session acquisition approach explicitly outside this milestone's safety rules.

## Next step

Decision required before a production upload version is scheduled.

The feasibility question can be reopened when at least one of the following exists:

1. Yandex publishes a supported programmatic own-track upload contract;
2. the pinned/approved client library exposes a documented upload API suitable for the existing token boundary;
3. the project owner performs an explicit, account-owned network capture of the normal website/desktop upload workflow and provides a sanitized request/response contract for analysis, without CAPTCHA/MFA/security-challenge bypass or cookie theft.

Until then, production provider upload capabilities remain disabled.
