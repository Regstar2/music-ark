# MusicArk v0.12.0 — External Metadata & Resilient Network Access

Status: implementation branch / Draft PR. No release, tag or production installer is created by this version.

## Goal

v0.12.0 adds a provider-neutral external metadata recovery layer for one Local Library file and a resilient network boundary for metadata APIs that may be unreachable directly. The existing Yandex metadata editor, Yandex upload transport, Matching, Variant, Coverage and Controlled Sync semantics remain separate and unchanged.

## External metadata resolver

The new `musicark.external_metadata` package contains normalized candidates, typed evidence, source adapters, fingerprinting, bounded cache, networking, WARP integration and a process bridge.

The resolver is cache-first and sequential. It does not call every service unconditionally. Its preferred path is:

```text
trusted cached/Yandex identity
-> cached or newly computed Chromaprint fingerprint
-> AcoustID (when the MusicArk application client key is available)
-> MusicBrainz Recording
-> distinct MusicBrainz Releases
-> optional fallback sources
```

A strong recording/release result causes early stop unless the caller explicitly requests more alternatives. External candidates never silently become a Yandex identity.

## Acoustic identification

`FingerprintService` invokes the official Chromaprint `fpcalc` executable and caches the fingerprint against local file size + modification time. The audio file itself is not sent to AcoustID by MusicArk; the lookup submits the fingerprint and duration. Missing or broken `fpcalc` degrades to text lookup instead of breaking Metadata Editor.

AcoustID uses an application client key. It is not a per-user MusicArk credential and ordinary end users should not be required to obtain one. Development builds can provide the key either through the OS keyring/Advanced Sources UI or through `MUSICARK_ACOUSTID_CLIENT_KEY`. The key is deliberately not committed to the repository.

For local PowerShell testing:

```powershell
$env:MUSICARK_ACOUSTID_CLIENT_KEY = '<application-client-key>'
flutter run -d windows
```

The environment variable is inherited by the Python bridge. Do not add the real key to tracked files, shell history snippets committed to the repository, or diagnostics.

## Sources

Implemented source boundaries:

- existing Yandex Music metadata gateway for an already trusted Yandex identity;
- AcoustID for acoustic identity hints when the MusicArk application client key is available;
- MusicBrainz for zero-config recording/release metadata;
- Cover Art Archive for zero-config release artwork discovery;
- ListenBrainz/MusicBrainz Mapper as an optional MetaBrainz fallback when the primary MusicBrainz endpoint cannot be reached;
- Discogs as an optional advanced release fallback requiring separate credentials;
- TheAudioDB as an optional low-priority fallback using its documented public free-tier key in development/free builds;
- Last.fm adapter retained as a deferred optional fallback and disabled unless an application API key is available.

An ordinary user must be able to use the default MusicBrainz + Cover Art Archive workflow without configuring provider API keys. Provider failures are isolated and represented as typed source states such as `not_configured`, `rate_limited`, `temporarily_unavailable` or `unavailable`.

## Confidence and evidence

External resolution uses categories rather than invented percentage certainty:

```text
exact
strong
possible
weak
ambiguous
```

Evidence types include acoustic fingerprint, exact Recording/Release MBID, ISRC and local metadata agreement signals. AcoustID identifies a recording candidate; it does not prove a particular album edition and it does not classify ORIGINAL/CENSORED.

## Compare and Apply

`ExternalMetadataEditor` reuses the existing transactional `MetadataEditorService.update(confirm=True)` write boundary. Empty external fields do not erase useful local values. Applying an external candidate does not bind or replace the trusted Yandex identity. The existing explicit Yandex Apply + Bind path stays separate.

## Network transport

`ExternalNetworkTransport` supports:

- `direct`;
- `custom_proxy` (HTTP/HTTPS/SOCKS5 through httpx);
- `warp` local proxy;
- `auto`.

Modern WARP Local Proxy is used through its localhost listener. MusicArk prefers HTTP CONNECT for MetaBrainz endpoints because it proved interoperable with TLS/SNI in real Windows testing; SOCKS5 remains a fallback where appropriate. TLS verification is never disabled.

`auto` tries Direct first and falls back only after transport failures such as connection/DNS/connect-timeout errors. Ordinary HTTP responses such as 401, 404 or 429 are not treated as proof of a network block. A short-lived per-host route-health cache avoids paying the same failed Direct timeout for every track.

Yandex upload Stage 1/Stage 2 is not routed through this subsystem.

## Cloudflare WARP

`WarpService` is Windows-specific and isolated from provider code. It detects `warp-cli`, reports typed status, can invoke supported mode/connect/disconnect commands, configures the Local Proxy listener when supported, and verifies readiness of the configured localhost proxy separately from human-readable CLI output.

The runtime install path is fail-closed:

1. discover a stable Windows download only from Cloudflare's official source;
2. require HTTPS and the expected Cloudflare download host;
3. download to a temporary directory;
4. require a valid Windows Authenticode signature whose signer contains Cloudflare;
5. invoke Windows Installer without shell interpolation;
6. re-detect WARP;
7. only then persist `installed_by_musicark=true`.

MusicArk does not patch Cloudflare binaries, emulate WARP registration, bypass Cloudflare consent/onboarding or disable TLS verification. If a required CLI capability cannot be established for the installed version, the integration must fail closed rather than guess a command.

## Ownership and future installer/uninstaller

`network_component_state` distinguishes a pre-existing WARP installation from one installed by MusicArk. A future production uninstaller must never remove WARP merely because it is present. It may offer removal only when MusicArk's ownership marker exists, with an option to keep WARP.

The production installer/uninstaller is intentionally not built in v0.12.0.

## Persistence

The core MusicArk database schema remains `1.9.0`. v0.12.0 adds an additive external metadata sub-schema identified by `external_metadata_schema_version=1`, containing:

- `local_external_identities`;
- `external_audio_fingerprints`;
- `external_metadata_cache`;
- `external_artwork_cache`;
- `network_component_state`.

Proxy/provider credentials are stored in the OS keyring when entered locally. Release/application credentials may instead be injected from the build/runtime environment. Non-secret network configuration is stored under `.musicark/network_settings.json`.

## Privacy

Depending on the selected sources, external services can receive search text such as artist/title/album or external identifiers. AcoustID receives a Chromaprint fingerprint and duration. MusicArk does not upload the local audio file to these metadata APIs.

## Known limitations

- Chromaprint `fpcalc` must currently be installed/available separately; packaging it is future installer work.
- The production MusicArk AcoustID application key has not yet been wired into release packaging; development can inject it securely at runtime.
- Last.fm is deferred: the adapter remains optional, but it is not required for v0.12.0 completion or the default metadata workflow. API-account availability must be revalidated before enabling it in a release build.
- Discogs remains an advanced optional fallback until a suitable application authentication path is chosen.
- TheAudioDB public free-tier key is acceptable only under its documented free/development conditions; terms must be rechecked before app-store/commercial distribution.
- External source commercial-use terms must be revalidated before monetized/public distribution.
- Cover Art Archive availability does not imply that cover images are copyright-free.
- Mobile VPN/WARP integration is not implemented; the network/provider layers remain platform-neutral and the Windows WARP adapter is isolated.
- This version does not add bulk metadata mutation, upload queue semantics, automatic censorship replacement, release packaging or auto-update.

## Tests

Offline tests cover additive migration, candidate/evidence serialization, fingerprint cache invalidation, Unicode file paths, invalid fpcalc output, proxy-secret persistence, HTTP-status vs transport-failure fallback behavior, WARP typed status and ownership tracking. CI must not actually change the runner VPN configuration.
